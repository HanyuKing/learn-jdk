# 发货时效配置技术设计

## 一、方案概要

将商品、类目发货时效从 Nacos 迁移到后台页面管理，业务查询统一通过 `DeliveryTimeService`，保持现有对外返回结构。

| 配置 | 持久化位置 | 运行时读取 |
|---|---|---|
| 类目时效 | `trade_pd_category.features`，TEXT 类型 JSON | 类目内存快照 |
| 商品独立时效 | Redis Hash，永久保存 | 商品内存快照 |
| 全局兜底文案 | 保留 Nacos `logisticsTime` | 原配置读取方式 |
| 变更记录 | `trade_operation_log` | 复用现有日志服务 |

最终规则：

```text
商品独立时效 → 商品直接类目时效 → 全局 logisticsTime → 默认30天
```

- 不继承父类目。
- 完全取消 `deliveryTimeDelay` 延迟叠加。
- 商品、类目均只有一个小时数，不增加 `specialHours`、`applyGlobalDelay` 或版本字段。
- 商品、类目缓存均由各实例 Spring 定时任务每分钟全量刷新，允许 1～5 分钟生效。
- **保存和清除使用独立接口，不使用 `deliveryHours=null` 表示清除。**
- 众筹项目规则不改，历史订单最晚发货时间快照不重算。
- 小红书调用接口不改，继续通过类目查询方法读取类目基础时效。

项目职责：

- **website-admin**：配置页面、回显、预览。
- **operation-platform**：认证、权限校验、调用 order-java。
- **order-java**：配置读写、内存缓存、时效计算、单个与批量查询、操作日志。

## 二、数据存储、缓存与操作日志

### 2.1 类目配置

新增字段：

```sql
ALTER TABLE trade_pd_category
    ADD COLUMN features TEXT NULL
    COMMENT '类目扩展配置，JSON格式';
```

JSON：

```json
{
  "deliveryTime": {
    "hours": 168
  }
}
```

约定：

- `hours` 为正整数，统一使用小时。
- `features` 为空或没有 `deliveryTime` 节点，表示未配置。
- 保存时只合并 `deliveryTime` 节点。
- 清除时删除该节点，保留其他功能配置；没有其他节点时保存 `{}`。
- 不增加配置版本，不扩展类目历史表。

类目保存、清除流程：

```text
开启数据库事务
    ↓
SELECT 类目 FOR UPDATE
    ↓
解析当前 features，修改 deliveryTime 节点
    ↓
更新 features、操作人、更新时间
    ↓
写入 trade_operation_log
    ↓
提交事务
```

锁行用于保护 JSON 合并，不进行版本比较。同一项配置后提交覆盖先提交。

原有类目名称、排序等通用更新不得顺带写回旧 `features`，该字段由专用更新方法维护。JSON 损坏时拒绝覆盖，不能按空对象处理。

### 2.2 商品配置

使用 Redis Hash：

```text
Key：trade:<deploymentId>:delivery-time:product
Field：productId
Value：小时数的十进制字符串
TTL：-1
```

示例：

```text
W2026092000023 → "360"
W2026092000022 → "168"
__initialized__ → "1"
```

约定：

- 不建商品时效数据库表。
- 不保存版本、删除标记或历史配置。
- 保存执行 `HSET`，清除执行 `HDEL productId`。
- 初始化标记用于区分合法空配置和整个 Hash 丢失，不能随最后一个商品清除而删除。
- 部署配置负责环境隔离。
- 不使用会自动设置 TTL 的缓存写入方法。

通过短 Lua 脚本原子完成：检查初始化标记、读取原值、保存或清除、返回原值。原值用于变更日志；不进行版本校验，后写覆盖。

### 2.3 内存缓存

维护两份不可变快照：

```java
AtomicReference<Map<Long, Integer>> categorySnapshot;

AtomicReference<Map<String, Integer>> productSnapshot;
```

| 缓存 | 刷新来源 | 频率 |
|---|---|---|
| 类目 | 查询未删除类目的 `id、features`，约 220 条 | 每分钟 |
| 商品 | Redis 一次 `HGETALL`，约 30 条 | 每分钟 |

刷新采用：

```text
读取完整数据 → 临时Map解析校验 → 构建不可变Map → 原子替换
```

具体要求：

- 新数据源模式下，首次加载成功后实例才进入可服务状态。
- 两个来源独立刷新，一方失败不影响另一方更新。
- 刷新失败保留旧快照，不先清空再加载。
- 合法空配置可以替换旧快照。
- Hash 缺失、初始化标记缺失、JSON 或数值非法时，不发布该来源的新快照。
- 业务查询未命中直接走下一优先级，不回源数据库或 Redis。
- 同一批请求各获取一次快照，循环内只做内存计算。
- 保存接口不直接修改本机快照，统一由定时任务刷新。
- 每个消费时效配置的实例均执行刷新，不能仅部署在独立 job 实例。
- 定时线程不读取请求 `AuthContext`。

后台回显直接读取持久化数据，可立即确认保存结果；运行时展示等待下一次刷新。

### 2.4 操作日志

统一复用 order-java 的 `OperationLogWriteService`，写入 `trade_operation_log`，不重复写 operation-platform 的 `biz_operation_log`。

| 字段 | 内容 |
|---|---|
| `biz_id` | 类目 ID 或商品 ID |
| `biz_system` | `PRODUCT` |
| `operation_type` | `CREATE`、`UPDATE`、`DELETE` |
| `operator` | 服务端认证的操作人 |
| `operation_details` | 对象类型、修改前后值、请求 ID |
| `created_at` | 操作时间 |

清除记录示例：

```json
{
  "module": "DELIVERY_TIME",
  "targetType": "PRODUCT",
  "targetId": "W2026092000023",
  "before": {
    "configured": true,
    "hours": 360
  },
  "after": {
    "configured": false
  },
  "requestId": "request-id"
}
```

只记录时效节点，不复制整个 `features`。补齐现有日志服务的操作时间映射，并检查保存结果。

失败与幂等规则：

- 类目配置和日志同事务，日志失败则回滚。
- 商品 Redis 修改成功后同步写日志；日志失败不回滚配置，记录完整错误并告警，保存接口仍返回配置已保存。
- 不增加日志补偿队列或分布式事务。
- 保存相同值、重复清除未配置项不重复记录变更日志。

## 三、业务解析与接口契约

### 3.1 时效解析

核心取值逻辑集中在 `DeliveryTimeServiceImpl`，增加内部统一小时数解析能力，供单个、批量及管理预览复用。

保留已有方法签名：

| 方法 | 职责 |
|---|---|
| `getDeliveryTimeSpecial(productId, categoryId)` | 按商品、类目、全局顺序获取配置，返回适配原展示层的文案 |
| `getDeliveryTime(String productId)` | 商品维度按统一优先级解析基础小时数 |
| `getDeliveryTime(Long categoryId)` | 仅取类目小时数，未配置返回 720，继续供小红书使用 |

商品、类目配置可转换为 `168小时` 这样的内部兼容文案；全局文案沿用现有解析器。全局文案非空但无法解析时，保持原有 30 天兼容兜底并记录异常。

修改 `ProductDeliveryDisplayServiceImpl`：

- 删除 `delayDay` 和 `getDeliveryTimeDelay()` 调用。
- `buildDisplayText` 删除延迟参数。
- 展示天数只由小时数换算。
- 保留现有 App 后缀及众筹项目优先处理。

从 `NacosConfig` 删除 `deliveryTimeDelay` 绑定，并更新相关测试。

保持现有展示和批量接口口径：

```text
展示天数 = max(1, ceil(基础小时数 / 24))
既有批量接口返回小时数 = 展示天数 × 24
```

例如配置 25 小时，站内展示 2 天，批量接口返回 48；小红书类目接口仍返回基础值 25。

### 3.2 配置接口

保留两端现有 Jackson `NON_NULL` 设置。**不区分保存请求中的“字段缺失”和“显式 null”，两者均作为非法保存请求。**

前端接口：

| 方法 | operation-platform 路径 | 请求内容 |
|---|---|---|
| GET | `/op/api/category/delivery-time/detail` | `categoryId` |
| POST | `/op/api/category/delivery-time/save` | `categoryId、deliveryHours` |
| POST | `/op/api/category/delivery-time/clear` | `categoryId` |
| GET | `/op/api/trade/product/delivery-time/detail` | `productId` |
| POST | `/op/api/trade/product/delivery-time/batch-detail` | 商品 ID 数组 |
| POST | `/op/api/trade/product/delivery-time/save` | `productId、deliveryHours` |
| POST | `/op/api/trade/product/delivery-time/clear` | `productId` |

order-java 内部接口统一使用前缀：

```text
/aigc/trade/internal/delivery-time
```

对应路径：

```text
/category/detail
/category/save
/category/clear
/product/detail
/product/batch-detail
/product/save
/product/clear
```

由专用 Feign Client 定义契约，operation-platform 转发调用。

保存请求示例：

```json
{
  "categoryId": 10045,
  "deliveryHours": 168
}
```

清除请求示例：

```json
{
  "categoryId": 10045
}
```

商品接口分别使用 `productId`，结构相同。

DTO 约束：

- 保存 DTO：`Integer deliveryHours` 使用 `@NotNull @Min(1)`。
- 清除 DTO：只定义对象 ID，不定义 `deliveryHours`。
- 类目 ID 校验非空，商品 ID 校验非空白。
- 小时数及“天转小时”计算进行溢出校验。
- 操作人从服务端认证上下文获取。
- 类目接口不接受完整 `features`。
- 前端、operation-platform、order-java 均不使用 null 清除语义。

清除行为：

- 对象不存在：返回业务错误。
- 对象存在但已经未配置：返回成功。
- 类目删除 `features.deliveryTime`；商品执行 `HDEL`。
- 重复清除不重复记录变更日志。
- 配置移除后的运行时效果由下一次缓存刷新体现。

### 3.3 回显契约

回显必须有明确的 `configured` 布尔字段，表示当前对象自身是否配置。

商品示例：

```json
{
  "productId": "W2026092000023",
  "configured": false,
  "categoryId": 10045,
  "categoryHours": 168,
  "effectiveHours": 168,
  "source": "CATEGORY",
  "logisticsTime": "预计7天内"
}
```

约定：

- `configured=true` 时返回 `configuredHours`。
- `configured=false` 时，`configuredHours` 可被 `NON_NULL` 省略，前端不能据此推断是否配置。
- `effectiveHours` 使用现有展示天数换算小时的口径。
- `source` 为 `PRODUCT / CATEGORY / GLOBAL / DEFAULT`。
- 管理回显直接读取数据库、Redis，预览复用统一解析逻辑。
- 保存和清除成功后返回更新后的配置详情。
- 批量管理回显最多 200 个商品，批量读取，不循环 RPC。

### 3.4 单个、批量运行时接口

保留：

```text
POST /aigc/trade/inner/product/batchGetDeliveryHours

请求：List<String>
响应：Result<Map<String, Integer>>
```

新增：

```text
GET /aigc/trade/inner/product/getDeliveryHours?productId=...

响应：Result<Integer>
```

两者使用相同有效时效口径。

批量流程保留现有商品基础信息批量查询，再使用两份内存快照计算。仅传商品 ID 时每 500 个分组查询；已知商品和类目时不增加数据库查询。

循环内没有 Redis、数据库或 RPC。单个商品不存在返回业务错误，批量缺失项不放入结果；原有批量读取已删除商品的能力保留。

## 四、运营页面

### 4.1 类目配置

在图 1 增加「类目特殊配置」Tab，提供：

- 一个发货时效输入：整数＋天/小时。
- 当前配置状态、预览及来源。
- 保存按钮：调用 `/save`。
- 清除按钮：调用 `/clear`，只提交类目 ID。

前端要求：

- 新 Tab 使用独立标识，不向原属性接口传 `type=4`。
- 非叶子类目的原属性空态不能遮挡配置入口。
- 明确仅作用于直接关联该类目的商品。
- 切换类目时忽略过时请求结果。
- 清除后按 `configured=false` 更新页面，不依赖响应中的 null 字段。

### 4.2 商品配置

在图 2 商品操作栏增加「时效配置」，弹窗支持：

- 商品独立时效：输入整数＋天/小时，调用 `/save`。
- 使用类目/全局时效：调用 `/clear`，只提交商品 ID。

展示商品、直接类目、配置来源和预计生效文案。

商品配置独立保存，不进入完整商品编辑、审核或发布流程。列表需要独立时效标记时，当前页统一一次批量回显。

### 4.3 共同要求

- 不展示延迟、特殊时效或版本相关输入。
- 整除 24 的小时数按天回显，否则按小时回显。
- 保存失败保留输入。
- 成功后提示“已保存，预计 1～5 分钟内生效”。
- 众筹项目类型 `CROWDFUNDING` 不开放本次修改入口，服务端同步校验。
- 本期不新增 B 端独立管理入口。
- 查看沿用现有管理权限，保存和清除使用操作权限，前后端共同校验。

## 五、迁移、发布与验收

### 5.1 数据迁移

| 原配置 | 新位置 |
|---|---|
| `deliveryTimeProduct` | Redis 商品 Hash |
| `deliveryTimeCategory` | 类目 `features.deliveryTime.hours` |
| `deliveryTimeCategoryDesc` | 解析后归并到同一个类目 `hours` |
| `logisticsTime` | 保留 Nacos |
| `deliveryTimeDelay` | 废弃，不迁移、不合并到配置值 |

同一类目同时存在基础时效和特殊文案时，按原站内特殊文案优先的顺序，采用特殊文案解析值。由此引起的小红书基础值变化列入迁移差异清单。

迁移需校验对象存在性、重复配置、文案解析及数值范围，支持预演和幂等检查，不覆盖迁移后人工修改。合并 `features` 时保留其他节点，实际变更写入 `trade_operation_log`。

初始化 Redis 标记并确认 TTL 为 `-1`。

### 5.2 发布与回滚

保留数据源开关：

```text
deliveryTime.configSource = NACOS | DB_REDIS
```

开关只控制配置来源；新代码中的优先级和取消延迟规则统一生效。切回 Nacos 不恢复延迟，完整恢复旧行为需要回滚应用版本。

发布顺序：

1. 新增 `features` 字段。
2. 预演并迁移配置。
3. 发布 order-java、Client、operation-platform。
4. 验证各实例两份快照。
5. 对比结果并切换新数据源。
6. 开放后台配置入口。
7. 稳定后清理废弃 Nacos 配置。

新模式下，配置未命中不逐项回退旧 Nacos 商品、类目值，防止清除后旧值重新生效。

回滚前暂停后台写入，导出上线后的配置差异；不删除新存储。

### 5.3 测试与验收

**接口及 Jackson/Feign 链路：**

- 使用项目实际 Jackson 配置和 Feign 编码器验证完整转发。
- 保存缺少 `deliveryHours`、显式传 null、传非正整数均被拒绝。
- 清除请求只带对象 ID，可完整转发并正确执行。
- 清除不存在对象返回错误；重复清除已存在但未配置的对象返回成功。
- 回显 `configured=false` 时，即使 `configuredHours` 被省略，页面仍正确展示未配置。
- 保存、清除权限均在后端生效。

**业务与存储：**

- 商品优先、直接类目匹配、全局兜底、默认 30 天正确。
- 旧 Nacos 中即使保留非零 `deliveryTimeDelay`，也不影响新结果。
- 配置 25 小时仍展示 2 天，既有批量接口返回 48。
- 修改、清除时效不损坏 `features` 的其他节点。
- 类目配置与日志同事务；商品日志失败不回滚配置且告警。
- 无实际变化不重复记录日志。

**缓存与性能：**

- 正常时效解析不访问数据库或 Redis。
- 批量循环无远程调用。
- 全量快照原子替换，失败保留旧值，合法清空正确生效。
- Hash 丢失不能被当作合法空配置。
- 各健康实例在 5 分钟内同步更新。
- 众筹规则、历史订单快照、C 端格式和小红书调用签名保持兼容。

完成相关后端测试、前端类型检查及目标环境构建。监控快照刷新时间、失败次数、配置解析失败、Redis Hash 缺失和日志写入失败；上线前核实 Redis AOF、备份及淘汰策略。
