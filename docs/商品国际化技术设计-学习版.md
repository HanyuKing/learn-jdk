## 0. 先建立坐标系：国际化到底在"化"什么

初学者最常见的误区是把"商品国际化"理解为"给 `product_name` 加一列 `product_name_en`"。所有大厂方案的第一步都是先把商品拆成三层，再决定每一层是否随语言/市场变化：

```text
┌──────────────────────────────────────────────────────────────┐
│ ① 身份层 Identity      productId / spuId / skuId / 类目ID / 属性ID │  不随任何维度变化
├──────────────────────────────────────────────────────────────┤
│ ② 内容层 Content       标题 / 描述 / 详情 / 图片Alt / 属性展示名     │  随 Locale 变化，允许回退
├──────────────────────────────────────────────────────────────┤
│ ③ 报价层 Offer         可售状态 / 价格 / 币种 / 税 / 物流 / 库存      │  随 Market 变化，禁止回退
└──────────────────────────────────────────────────────────────┘
```

两条铁律，几乎所有大厂方案都遵守：

1. **身份不变**：一个商品在全球只有一个 ID。Amazon 的 ASIN [R6]、Lazada 的 Global SKU [R13]、AliExpress 的 Product ID [R12] 都是跨站点稳定的。身份一旦随语言或国家复制，订单、库存、售后、报表全部要跟着复制。
2. **内容和报价是两个正交维度**：`Locale`（人看什么语言）和 `Market`（货卖给谁、收什么钱）不是一回事。一个美国用户可以用中文看美国站，一个加拿大市场可以同时有 en-CA 和 fr-CA。把两者绑成一个"站点"是早期方案，扩展到第 5 个国家时就会爆炸。

对照本仓库，这三层目前的状态：

| 层 | 本仓库现状 | 评价 |
|---|---|---|
| 身份 | `trade_pd_product.product_id`、`trade_pd_sku.sku_id`、`trade_pd_category.id`、`trade_pd_attribute.id/code` | ✅ 已满足，`Attribute.code` 字段尤其有价值 |
| 内容 | 直接存在主表 `product_name/description`、`ProductExt.detail`；`trade_pd_product_language` 表已建但无调用方 | ⚠️ 结构已埋好，链路没接 |
| 报价 | `Product.price`/`Sku.price` 为 `BigDecimal` 元、无 currency；`trade_pd_product_region` 有可售状态和运费但无调用方；支付写死 `CNY` | ❌ 缺市场维度，币种是隐式的 |

## 1. 大厂方案横向对比

### 1.1 阿里系：从 CPV 模型到 Global/Venture 两级商品

**淘宝/天猫商品中心（国内基础）**
公开资料里最经典的是 CPV 模型（Category-Property-Value）[R10]，虚拟类目/前后台类目分离的思路见 [R11]：

```text
类目 Category ──┬── 关键属性 (决定 SPU)     如：品牌、型号
               ├── 销售属性 (决定 SKU)     如：颜色、尺码
               └── 非关键属性 (仅展示)     如：材质、适用人群
```

属性和属性值都是**带 ID 的字典**，商品只引用 ID，展示名在字典里。这一步在国内看起来是"过度设计"，但它正是后来多语言几乎零成本的原因：翻译一次 `属性值 silver → Sterling Silver`，全站所有引用它的 SKU 自动生效。

> 本仓库映射：`trade_pd_attribute(code, name, unit)` + `trade_pd_attribute_option(option_id, value)` 已经是字典；但 `trade_pd_sku_attribute(attribute_name, attribute_value)` 和 `trade_pd_product_attribute` 存的是**文本快照**（见 `SkuAttribute.java`、`ProductAttribute.java`），引用关系断了。这是国际化前最值得补的一刀。

**AliExpress（跨境出口，单平台多语言）**
对外可见的模型（来自卖家中心和开放平台 [R12]）：

- 一个商品一个 Product ID，卖家用源语言（通常中文或英文）发布。
- 平台机翻到 18+ 种语言，卖家可以逐语言人工覆盖标题/详情（"多语言编辑"）。
- 买家端由「语言 + 币种 + 收货国」三元组决定展示，三者独立可切换——这正是 Locale 与 Market 正交的直接证据。
- 价格按币种用平台汇率展示，但结算以卖家设定的基准币种为准（美元），平台负责换汇。

学习点：**源语言 + 衍生翻译 + 人工覆盖** 是跨境出口平台的标准三段式；"机翻先行、人工可覆盖、覆盖后不被机翻冲掉"是状态机的核心约束（第 5 节展开）。

**Lazada（东南亚多站点）**
开放平台和卖家中心公开的概念是 Global Product / Global SKU 与各国站点（Venture）的本地商品 [R13]：

```text
Global SKU (身份 + 源内容)
   ├── 🇸🇬 SG listing：本地标题(en) / SGD 价格 / SG 可售 / SG 库存
   ├── 🇹🇭 TH listing：本地标题(th) / THB 价格 / TH 可售 / TH 库存
   └── 🇮🇩 ID listing：本地标题(id) / IDR 价格 / ID 可售 / ID 库存
```

每个 Venture 是一套相对独立的运营实体（独立 App、独立运营、独立合规），所以内容和报价都按站点落地，Global 层只负责身份和同步。

学习点：当**市场之间差异大于相似**（法规、语言、运营团队都不同）时，"每站点一份 listing"反而比"全局内容 + 回退"更稳；代价是数据量 × 站点数。

### 1.2 京东：主数据中心 + 跨境双向

京东公开技术分享中反复出现的是"商品主数据 / SKU 中心"的概念 [R14][R15]：SKU 是唯一身份，基础信息（名称、类目、品牌、属性）集中管理，各业务线（自营、POP、国际、工业品）通过**扩展属性**挂载自己的字段，而不是复制主表。

跨境业务有两个方向，对模型要求不同：

| 业务 | 方向 | 对商品模型的要求 |
|---|---|---|
| 京东国际（进口）[R16] | 海外商品 → 中国消费者 | 商品必须有**合规中文信息**（原产地、海关备案、中文标签），本质是"外文源内容 + 中文目标内容 + 合规字段" |
| 京东全球售（出口） | 中国商品 → 海外消费者 | 多语言 + 多币种 + 海外履约 |

学习点：**合规字段是内容层的一部分，但它不走语言回退**——缺了就是不可售，不能用源语言兜底。这是和"营销文案可以回退"最大的区别，本仓库设计里对应 `ProductRegion.complianceStatus`。

> 「推断」京东 SKU 中心按业务线扩展属性的方式，与本仓库 `trade_pd_product_ext.extra` JSON 扩展字段思路一致；区别在于京东的扩展属性有 schema 注册，不是自由 JSON。

**京东对外分享过的国际化一手资料**（都在京东云开发者社区，值得精读）：

| 文章 | 核心主张 | 对本仓库的直接启示 |
|---|---|---|
| 《京东多语言质量解决方案》（京东全球售项目组，2026-01）[R23] | 文案以 Key 进翻译平台；客户端 SDK 取"国家 / 语言 / 模式"三参数，经网关和 JSF **隐式传参**到后端，后端从全局上下文 SDK **只读**；汇率换算规则：外币 = 本币 × 汇率，VND/KRW/JPY 取整、其余最多两位小数；汇率接口 80ms 超时则**降级不展示**；用大模型做翻译质检，三轮优化后采纳率 11% → 85.71% | ① "隐式传参 + 只读上下文"就是本篇 2.5 节 `MarketContext` 走 Feign `X-Auth-*` 透传的思路；② 币种精度按 ISO 4217 取整与 3.3 节 `Money` 一致；③ 汇率/价格依赖要有超时降级；④ 翻译质检可以上 LLM，但要有采纳率指标 |
| 《系统国际化之多语言解决方案》（京东物流 高耀飞，2024-05）[R24] | **反对在数据库里给同一词条存多套语言**：后端只返回错误 code 和业务描述，前端按当前语言渲染；语言通过 `Accept-Language`（HTTP）/ `RpcContext`（JSF）由拦截器统一解析，**不要放进业务参数**；建国际公共词条库，高频词条 GPT 翻译 + 人工校对，翻译先查词库再用 GPT | 这篇讲的是 **系统文案**（菜单、按钮、错误提示），不是商品内容。它的"不要在 DB 存多语言"结论对系统文案成立，对商品标题/详情**不成立**（见 2.4 节）。两类文本要分开治理：系统文案走 `MessageSource` + 前端词条，商品内容走 `ProductLanguage` 表 |

另外两份偏商品系统本身而非国际化的京东资料：InfoQ 收录的《京东 11.11：商品搜索系统架构设计》[R25]，以及 QCon+ 2022《京东到家商品架构演进实践》（孙岩，商品系统单体 → 微服务 + DDD 四色建模）[R26]。

### 1.3 Amazon：ASIN 全球唯一 + 按 Marketplace 独立 listing

Amazon 是"身份全局、内容和报价按市场"的最典型实现，且因为 SP-API 完全公开 [R6]，模型非常清晰：

- **ASIN** 是全球唯一身份（同一本书在 US/JP/DE 是同一个 ASIN）。
- 每个 **Marketplace**（`ATVPDKIKX0DER` = US，`A1VC38T7YXB528` = JP，见 [R7]）有自己的 catalog item：标题、要点、描述、图片都带 `marketplaceId + languageTag`（如 `en_US`、`ja_JP`）[R6]。
- 价格、库存、可售状态（offer）完全按 marketplace 独立，不存在"美国有价所以日本可售"。
- **Build International Listings（BIL）** 工具可以把源市场 listing 同步到目标市场，并按规则（固定汇率 / 汇率 + 百分比 / 独立定价）生成目标价格，且**汇率变动时自动调价** [R9]。

学习点：
1. Amazon 把 marketplace 当作内容和报价的**共同分区键**，但 language 仍然是 marketplace 之下的独立维度（加拿大站 en_CA/fr_CA）。
2. BIL 的"同步规则"思想值得借鉴：源市场变更 → 目标市场按规则**派生**，派生结果可被人工覆盖，覆盖后不再被同步覆写。这和 AliExpress 的翻译覆盖是同一个模式，只是作用在价格上。

### 1.4 Shopee：GSP 全球商品 + SIP 自动派生

Shopee 卖家中心与开放平台公开的跨境模式 [R17][R18]：

- **GSP（Global Selling Platform）**：卖家维护一份全球商品（源语言、基准价）。
- **SIP（Shopee International Platform）**：平台自动把商品派生到其他站点——自动翻译标题、按汇率 + 费率自动定价、库存联动。卖家只运营主站，派生站点由平台托管。

学习点：**派生（Derivation）是一等公民**。源 → 目标不是"复制一次"，而是持续的、带规则的、可人工打断的同步关系。本仓库若未来做"中文站为源、英文站派生"，`ProductLanguage.version` + `source_version` 的版本对就是这个关系的最小实现。

### 1.6 两大流派与本仓库的选型

把上面收敛一下，其实只有两个流派：

```text
流派 A：单主数据 + 多语言内容 + 市场覆盖          流派 B：全局商品 + 每站点独立 listing
  (AliExpress / 京东 / 本仓库推荐)                   (Lazada / Amazon / Shopee)

  Product ──┬── Content[zh-CN]                      GlobalProduct
            ├── Content[en-US]                          ├── Listing[US] {content, offer}
            ├── Content[ja-JP]                          ├── Listing[JP] {content, offer}
            └── Offer[US] / Offer[JP] / ...             └── Listing[DE] {content, offer}
```

| | 流派 A | 流派 B |
|---|---|---|
| 数据量 | 商品 × 语言数 + 商品 × 市场数 | 商品 × 站点数（内容+报价都复制） |
| 一个语言多个市场复用 | 天然支持（en 给 US/UK/SG 共用） | 要复制 3 份 |
| 一个市场多语言 | 天然支持（CA: en/fr） | 要在 listing 内再分语言 |
| 市场间差异很大时 | 需要"区域覆盖版本"补丁 | 天然隔离 |
| 运营团队按国家划分 | 权限要按市场切 | 天然对齐 |
| 适合阶段 | 2~10 个市场、语言少于市场、团队集中 | 站点各自有独立运营/合规团队 |

**本仓库选 A**，理由不是"A 更先进"，而是：
1. 当前只有 bj（中国）/ rf（海外 hitems.ai）两套部署，市场数量少，运营团队集中。
2. `trade_pd_product_language` 和 `trade_pd_product_region` 两张表在 2025-05 就是按 A 的形状建的（分别是 Content 和 Offer）。
3. 流派 B 一旦选了就很难回到 A（listing 之间的数据漂移不可逆）；A 在需要时可以给某个市场加"区域覆盖版本"（`region_code` 非空的 Content 行）来局部获得 B 的隔离性。

### 2.2 三层模型落到本仓库的表

```text
身份层    trade_pd_product (product_id, spu_id, category_id, product_type, status, audit_status, channel ...)
          trade_pd_sku     (sku_id, product_id, ...)
          trade_pd_attribute / trade_pd_attribute_option / trade_pd_category

内容层    trade_pd_product_language   (product_id, locale, region_code=GLOBAL|xx, name, desc, detail, files, 翻译状态, 版本)
          [新] trade_pd_attribute_i18n        (attribute_id, locale, name, unit)
          [新] trade_pd_attribute_option_i18n (option_id,    locale, display_value)
          [新] trade_pd_category_i18n         (category_id,  locale, name, path_name)
          兼容：trade_pd_product.product_name/description 视为 zh-CN 的只读镜像

报价层    trade_pd_product_region     (product_id, market_code, region_code, sale_status, currency, tax_mode, 物流, 合规, 版本)
          [新] trade_pd_sku_market_price (sku_id, market_code, currency, list_amount, sale_amount, tax_included, 生效区间, 版本)
          库存：沿用 StockReadService，增加 market/仓 维度

快照层    trade_order_item (+ market_code, locale, currency_code, catalog_version, 本地化名称/属性快照)
```

设计上三个值得记住的"为什么"：

**为什么内容表要有 `region_code`，默认 `GLOBAL`？**
AliExpress 式的"一个语言全市场共用"是主流，但总有例外：英国站要写 "jewellery"、美国站写 "jewelry"；欧盟要求材质合规文案。给内容表加一个默认 `GLOBAL` 的 `region_code`，就能在不切换流派的前提下，对个别市场做"覆盖版本"。读取时回退链多一跳：`(en-US, US) → (en-US, GLOBAL) → (en, GLOBAL) → ...`。

> 注意用 `GLOBAL` 字面值而不是 `NULL`：MySQL 唯一索引中多个 `NULL` 互不冲突，`UNIQUE(product_id, locale, region_code)` 会失效。

**为什么属性值一定要编码化？**
看一个具体例子。本仓库 SKU 属性现在存的是：

```text
sku_attribute: {attribute_name: "材质", attribute_value: "纯银"}
```

要翻成英文，只能逐 SKU 改文本，而且 "纯银" / "925银" / "纯银 " 三种写法会被当成三个值。编码化之后：

```text
sku_attribute: {attribute_id: 17, option_id: 1703}
attribute_i18n:        (17,   zh-CN, "材质")   (17,   en-US, "Material")
attribute_option_i18n: (1703, zh-CN, "纯银")   (1703, en-US, "Sterling Silver")   (1703, ja-JP, "スターリングシルバー")
```

翻一次全站生效，搜索筛选（ES 的 terms 过滤）也从"按文本"变成"按 ID"，不再受语言影响。这正是淘宝 CPV 模型在国际化上的红利。

**为什么不把价格放进语言表？**
"美元价格"不是英文内容的一部分：新加坡用英文但用 SGD；加拿大用英/法文但都用 CAD。价格的分区键是 Market，不是 Locale。把 `price_usd` 放进 `product_language(en-US)` 是最常见的新手错误，后果是 en-GB 和 en-US 不得不复制两份内容只为了价格不同。

### 2.3 Locale：规范化、回退链、按字段回退

**标准**：BCP 47（RFC 5646）[R1]，形式 `language[-Script][-REGION]`，例：`zh-Hans-CN`、`en-US`、`ja-JP`。CLDR（Unicode 的本地化数据仓库）[R2] 提供了标准回退规则和数字/货币/日期格式。

本仓库现在有三种写法混用，这是第一个要统一的地方：

| 来源 | 值 | 文件 |
|---|---|---|
| `jjewelry.resource.locale.language` | `zh-Hans` / `en` | `application-*_bj.yml:83`、`*_rf.yml` |
| `locale.lang` | `zh-CN` / `en-US` | `application-*_bj.yml:145` |
| `ProductLanguage.languageCode` | 未定义（空表） | — |
| `Locale.CHINESE` 硬编码 | `zh` | `push/PushService.java:40`、`SpringContextHolder.java:160` |

规范化器要做的事（Java 8 的 `Locale.forLanguageTag` + `toLanguageTag` 已经够用 [R4]）：

```java
package cn.mathmagic.jjewelry.business.productdomain.i18n;

import java.util.Locale;
import org.springframework.util.StringUtils;

/**
 * Locale 规范化：统一为 BCP47 形式（en-US / zh-CN / ja-JP）。
 * 入口来源可能是 Accept-Language、x-language 头、配置文件，写法各异，必须先规范化再参与查询和缓存 key。
 */
public final class LocaleNormalizer {

    private LocaleNormalizer() {}

    public static String normalize(String raw) {
        if (!StringUtils.hasText(raw)) {
            return null;
        }
        // Accept-Language 可能带权重: "en-US,en;q=0.9,zh-CN;q=0.8" —— 只取第一个
        String first = raw.split(",")[0].trim();
        Locale locale = Locale.forLanguageTag(first.replace('_', '-'));
        if (!StringUtils.hasText(locale.getLanguage())) {
            return null; // 非法 tag，交给上层走默认
        }
        // zh-Hans → zh-Hans-CN 这类脚本补全交给白名单映射，这里只做大小写与分隔符规范
        return locale.toLanguageTag();
    }
}
```

**回退链**（以请求 `en-GB`、市场 `UK` 为例）：

```text
en-GB@UK → en-GB@GLOBAL → en@GLOBAL → (UK 市场默认 Locale, 如 en-US)@GLOBAL → 源语言 zh-CN (主表兼容字段)
```

实现上不要在 Service 里写 if-else，而是**先算出有序候选列表，再一次 `IN` 查询，在内存里按候选顺序挑**：

```java
package cn.mathmagic.jjewelry.business.productdomain.i18n;

import java.util.ArrayList;
import java.util.LinkedHashSet;
import java.util.List;
import java.util.Locale;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Component;

/**
 * 计算 Locale 回退候选链。顺序即优先级，去重后返回。
 * 市场默认 Locale 和源语言从 Nacos 配置读取（见 NacosI18nConfig，TODO）。
 */
@Component
@RequiredArgsConstructor
public class LocaleFallbackChain {

    private final NacosI18nConfig i18nConfig;

    public List<String> resolve(String requestLocale, String marketCode) {
        LinkedHashSet<String> chain = new LinkedHashSet<>();
        if (requestLocale != null) {
            chain.add(requestLocale);                                   // en-GB
            Locale l = Locale.forLanguageTag(requestLocale);
            if (l.getCountry().length() > 0) {
                chain.add(new Locale(l.getLanguage()).toLanguageTag()); // en
            }
        }
        chain.add(i18nConfig.getMarketDefaultLocale(marketCode));       // en-US
        chain.add(i18nConfig.getSourceLocale());                        // zh-CN
        return new ArrayList<>(chain);
    }
}
```

**按字段回退 + 完成度门槛**：大厂不会因为详情没翻译就把整页回退成中文，而是逐字段挑。但也不会允许"标题是英文、销售属性是中文"这种半成品上线——所以有**必填字段集合**的概念：

| 字段 | 是否必填 | 缺失时 |
|---|---|---|
| 标题、销售属性名/值 | 必填 | 该 Locale 视为"未就绪"，整体回退到下一候选 |
| 短描述、详情、图片 Alt | 可选 | 单字段回退，并在响应 `fallbackFields` 里标出 |
| 合规文案（材质、过敏提示） | 市场必填 | 不回退；缺失 → 该市场不可售 |

响应里带上元信息，运营才能分清"是翻译缺失还是程序 bug"：

```json
{ "locale": "en-GB", "resolvedLocale": "en", "marketCode": "UK", "fallback": true, "fallbackFields": ["detail"] }
```

### 2.4 四种存储方案对比（为什么选"语言表"）

| 方案 | 形态 | 优点 | 致命缺点 | 谁在用 |
|---|---|---|---|---|
| ① 列扩展 | `name_zh, name_en, name_ja` | 最简单，一次查询 | 加语言 = DDL；无法记录每语言的审核状态/版本 | 小系统 |
| ② JSON 列 | `name_i18n: {"zh-CN":..,"en-US":..}` | 加语言不改表 | 无法建唯一约束、无法按语言索引、搜索要展开；审核状态还是没地方放 | 内容型 CMS 的次要字段 |
| ③ 语言表（本仓库） | `product_language(product_id, locale, ...)` | 每语言独立版本/状态/审核；可建唯一键；批量 IN 查询 | 多一次查询（但可批量） | AliExpress 风格 |
| ④ 按国家复制表 | `product_us, product_jp` 或 `product(country_code)` | 隔离彻底 | 身份复制 → 订单/库存/售后全复制；跨国报表要 UNION | Lazada/Shopee 站点级 |

落地版第 12.2/12.3 节已给出结论，这里补一句学习要点：**③ 不是最省事的，而是唯一能承载"翻译是一个有状态的工作流"的方案**。①② 能存文本，但存不下"这个英文标题是机翻的还是人审过的、对应源版本是多少"。

> 容易混淆的一点：京东物流那篇 [R24] 明确反对"在数据库里给同一词条存多套语言"。它说的是**系统文案**（菜单、按钮、错误码），这类文本数量有限、随版本发布、不需要审核流——用资源文件 + 前端词条确实更合适，本仓库的 `i18n/messages_*.properties` 和 `CommonJsonObject(ErrorCodeEnum)` 就属于这一类。**商品内容**则是海量、运营随时改、每条要走翻译审核，必须落表。两类文本用两套机制，别混。

### 2.5 代码骨架：MarketContext 与请求上下文接入

大厂的"站点上下文"都在网关层解析一次，然后沿调用链透传——京东全球售的做法是客户端 SDK 取国家/语言/模式，经网关和 JSF 隐式传参，后端从全局上下文 SDK 只读 [R23]；京东物流也强调语言由拦截器从 `Accept-Language`/`RpcContext` 统一解析、不要放进业务参数 [R24]。本仓库已经有两条现成的透传管道，不要新建第三条：

| 管道 | 来源 | 写入点 | 跨服务透传 | 本仓库现状 |
|---|---|---|---|---|
| `AuthContext`（uc-auth-sdk） | `x-language` 头，兜底 `Accept-Language` | jar 内 `ClientContextFilter` | Feign 拦截器把全部 key 写成 `X-Auth-<KEY>` 头，`AuthContextFilter.java:42-54` 在 `/inner`、`/internal` 还原 | `getLanguage()` 存在但**零调用** |
| `RequestHeaderContext`（jjewelry-api-common） | `Accept-Language`，默认 `${locale.lang}` | jar 内 `HeaderInterceptor` | 不透传 | 只被错误码文案用 |

推荐：**以 `AuthContext.getLanguage()` 为主**（因为它已经随 Feign 透传，内部服务调用不会丢），`RequestHeaderContext` 作为兜底；两者都没有时取 `locale.lang` 配置。MarketContext 本身是一个**不可变的值对象，作为方法参数显式传递**，不要再塞进 ThreadLocal——这是和 `AuthContext` 子线程污染风险（AGENTS.md 第 2 条）对齐的做法。

```java
package cn.mathmagic.jjewelry.business.productdomain.i18n;

import lombok.Builder;
import lombok.Value;

/**
 * 市场上下文：一次商品读/写请求的"站点坐标"。
 * 不可变；由 MarketContextResolver 在 Controller/Facade 入口解析一次，然后作为参数显式传递。
 * 刻意不放 ThreadLocal：线程池/CompletableFuture 场景下避免 AuthContext 式的上下文污染。
 */
@Value
@Builder
public class MarketContext {
    /** 销售市场，如 CN / US / UK；决定可售、价格、币种、税 */
    String marketCode;
    /** 履约区域（国家/地区码），沿用 ProductRegion.regionCode 体系 */
    String regionCode;
    /** BCP47，已规范化，如 en-US；决定内容 */
    String locale;
    /** ISO 4217，如 USD；通常由 market 推出，允许用户覆盖展示币种 */
    String currencyCode;
    /** 现有渠道字段 APP / WEB / XHS */
    String channel;
}
```

```java
package cn.mathmagic.jjewelry.business.productdomain.i18n;

import cn.mathmagic.jjewelry.business.auth.util.AuthContext;
import cn.mathmagic.jjewelry.common.config.RequestHeaderContext;
import lombok.RequiredArgsConstructor;
import lombok.extern.slf4j.Slf4j;
import org.springframework.stereotype.Component;
import org.springframework.util.StringUtils;

/**
 * 解析 MarketContext。优先级：显式参数 > 用户已选市场(TODO 用户资料) > AuthContext/RequestHeaderContext 头 > 站点默认。
 * 只在请求线程调用；子线程通过参数拿已解析好的 MarketContext。
 */
@Slf4j
@Component
@RequiredArgsConstructor
public class MarketContextResolver {

    private final NacosI18nConfig i18nConfig;

    public MarketContext resolve(String explicitMarket, String explicitLocale, String explicitCurrency) {
        String locale = LocaleNormalizer.normalize(explicitLocale);
        if (locale == null) {
            locale = LocaleNormalizer.normalize(AuthContext.getLanguage());       // x-language，随 Feign 透传
        }
        if (locale == null) {
            locale = LocaleNormalizer.normalize(RequestHeaderContext.getLanguage()); // Accept-Language 兜底
        }
        String market = StringUtils.hasText(explicitMarket) ? explicitMarket : i18nConfig.getDefaultMarket();
        if (locale == null || !i18nConfig.isSupportedLocale(locale)) {
            log.debug("locale {} unsupported, fallback to market default", locale);
            locale = i18nConfig.getMarketDefaultLocale(market);
        }
        String currency = StringUtils.hasText(explicitCurrency) ? explicitCurrency : i18nConfig.getMarketCurrency(market);
        return MarketContext.builder()
                .marketCode(market)
                .regionCode(market) // TODO 市场与履约区域解耦后从配置映射
                .locale(locale)
                .currencyCode(currency)
                .channel(AuthContext.getClient())
                .build();
    }
}
```

**本地化内容解析器**（批量、一次查询、内存挑选）：

```java
package cn.mathmagic.jjewelry.business.productdomain.service.read;

import cn.mathmagic.jjewelry.business.productdomain.entity.ProductLanguage;
import cn.mathmagic.jjewelry.business.productdomain.i18n.LocaleFallbackChain;
import cn.mathmagic.jjewelry.business.productdomain.i18n.MarketContext;
import cn.mathmagic.jjewelry.business.productdomain.repository.ProductLanguageRepository;
import java.util.Collection;
import java.util.Comparator;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.function.Function;
import java.util.stream.Collectors;
import lombok.RequiredArgsConstructor;
import org.springframework.stereotype.Service;

/**
 * 批量解析商品本地化内容。列表页 N 个商品只打一次 DB，禁止在循环里逐个查 ProductLanguage。
 */
@Service
@RequiredArgsConstructor
public class ProductLocalizedContentResolver {

    private final ProductLanguageRepository productLanguageRepository;
    private final LocaleFallbackChain fallbackChain;

    /**
     * @return productId -> 命中的语言行（按回退链优先级挑选）；未命中则不在 map 里，调用方回退到主表字段
     */
    public Map<String, ProductLanguage> resolve(Collection<String> productIds, MarketContext ctx) {
        List<String> chain = fallbackChain.resolve(ctx.getLocale(), ctx.getMarketCode());
        // TODO 仓储补一个 listPublished(productIds, locales, regionCodes) 的 IN 查询
        List<ProductLanguage> rows = productLanguageRepository.listPublished(productIds, chain, ctx.getRegionCode());

        Map<String, Integer> rank = chainRank(chain);
        return rows.stream().collect(Collectors.groupingBy(
                ProductLanguage::getProductId,
                Collectors.collectingAndThen(
                        Collectors.minBy(Comparator.comparingInt(r -> rank.getOrDefault(r.getLocale(), Integer.MAX_VALUE))),
                        Optional::get)));
    }

    private Map<String, Integer> chainRank(List<String> chain) {
        return chain.stream().collect(Collectors.toMap(Function.identity(), chain::indexOf));
    }
}
```

## 3. 站点 / 市场 / 币种模型（深入）

### 3.1 先把五个词分开

| 术语 | 含义 | 举例 | 决定什么 |
|---|---|---|---|
| Site / 站点 | 一套前端 + 域名 + 部署 | `zaohaowu`（bj）/ `hitems.ai`（rf） | 入口、默认市场和 Locale |
| Market / 市场 | 卖给谁、按谁的规则结算 | US、UK、EU、JP | 可售、价格、币种、税、合规 |
| Region / 履约区域 | 货从哪发、能发到哪 | 中国仓、新加坡仓、US 本土 | 物流、运费、时效 |
| Locale | 用户看什么语言/格式 | en-US、fr-CA | 内容、日期/数字格式 |
| Currency | 用什么币标价和收款 | USD、JPY | 金额精度、支付通道 |

常见关系：一个 Site 默认一个 Market；一个 Market 一个结算币种、一个或多个 Locale、一个或多个履约 Region。Amazon 的 marketplace 大致 = Market，Lazada 的 Venture ≈ Site + Market 合一。

本仓库现在的形态是**"按部署隔离站点"**：bj 和 rf 两套 `application-*.yml`、两套域名、两个对象存储区域，但连同一个库名 `jjewelry_produce`（host 由环境变量注入，大概率是两套库）。这相当于流派 B 的最粗粒度版本——站点之间什么都不共享，包括商品身份。它的问题是"同一个商品要在两边各建一次"。国际化的第一步其实不是加语言，而是**把 Market 从部署维度变成数据维度**。

### 3.2 报价层：ProductRegion → 市场报价（Offer）

`ProductRegion` 目前的字段（`status/shippingMode/freightSetting/unifiedFreightPrice`）其实已经是 Offer 的一半（可售 + 物流），缺的是另一半（币种、税、合规）。对比 Amazon 的 offer 模型，建议补：

```sql
    ADD COLUMN currency_code     char(3)      NULL COMMENT 'ISO 4217',
    ADD COLUMN tax_mode          tinyint      NOT NULL DEFAULT 1 COMMENT '1=含税展示 2=不含税展示',

```

**销售资格不回退**是这一层最重要的规则，而且要在**三个地方同时判断**，否则会出现"搜索能搜到、详情能打开、下单被拒"的割裂：

1. ES 文档里带 `marketCode + saleStatus`，召回时过滤。
2. 详情 `getProductDetailResp` 在现有 `商品未上架!` 校验（`ProductReadServiceImpl.java:408`）旁边加市场可售校验。
3. 下单 `/product/detail`（预下单）再校验一次，以这次为准。

### 3.3 价格：Money、独立定价 vs 派生定价、含税展示

**Money 值对象**。本仓库所有金额是裸 `BigDecimal`（`Product.price`、`Sku.price`、`OrderItem.price`），币种是隐式的 CNY（`WechatNativePayment.java:119` 等 6 处写死）。国际化后"一个 BigDecimal 不知道自己是什么币"会导致 USD 100 和 JPY 100 相加。大厂做法是领域层用 `Money(amount, currency)`，DB 继续两列：

```java
package cn.mathmagic.jjewelry.business.common.money;

import java.math.BigDecimal;
import java.math.RoundingMode;
import java.util.Currency;
import lombok.Value;

/** 金额值对象。精度来自 ISO 4217（JPY 0 位、USD 2 位、KWD 3 位，见文档 [R3][R4]），禁止跨币种算术。 */
@Value
public class Money {
    BigDecimal amount;
    Currency currency;

    public static Money of(BigDecimal amount, String currencyCode) {
        Currency c = Currency.getInstance(currencyCode);
        return new Money(amount.setScale(c.getDefaultFractionDigits(), RoundingMode.HALF_UP), c);
    }

    public Money add(Money other) {
        if (!currency.equals(other.currency)) {
            throw new IllegalArgumentException("currency mismatch: " + currency + " vs " + other.currency);
        }
        return of(amount.add(other.amount), currency.getCurrencyCode());
    }

    /** 对接支付通道时的最小单位（分/円）；替代现有 multiply(100).intValue() */
    public long toMinorUnit() {
        return amount.movePointRight(currency.getDefaultFractionDigits()).longValueExact();
    }
}
```

> 现有 `BasePayment.java:124` 的 `multiply(100).intValue()` 对 JPY 是错的（JPY 没有小数位，×100 会多付 100 倍）。这是国际化必须改的"隐藏的 CNY 假设"之一。京东全球售公开的规则也是同样的处理：VND/KRW/JPY 取整、其他币种最多两位小数 [R23]。

**独立定价 vs 派生定价**。三家做法：

| | 方式 | 适合 |
|---|---|---|
| Amazon 独立定价 [R9] | 每个 marketplace 手工设价 | 运营有精力、市场差异大 |
| Amazon BIL [R9] / Shopee SIP [R17] 派生 | 目标价 = 源价 × 汇率 × (1 + 加价率) + 固定费，汇率变化自动重算 | 市场多、商品多 |
| AliExpress 展示换汇 [R12] | 结算币固定 USD，展示币种按汇率换算 | 卖家只想维护一个价 |

本仓库建议**第一阶段用派生定价、落库为独立价**：`trade_pd_sku_market_price` 存最终 USD 价，由 Job 按规则从 CNY 派生，人工改过的行打 `manual_override=1` 不再被派生覆盖（又是"派生 + 人工覆盖"模式）。**不要在读链路实时乘汇率**——汇率变化会让购物车里的价格和详情页不一致，且无法复现历史价格。如果某些展示场景确实要实时换汇（例如"约合 ¥xxx"的参考价），按京东的做法给汇率接口设超时（他们是 80ms），超时就不展示而不是阻塞主链路 [R23]。

**含税/不含税展示**是容易漏的市场规则：欧盟/英国/日本/澳洲法律要求**含税价展示**，美国/加拿大习惯**不含税**，结算时按州/省加税。这意味着 `tax_mode` 是市场属性而不是商品属性，详情页返回的 `price` 必须说明是 inclusive 还是 exclusive。

**接入点**：`PriceService.getPrice(ProductContextDto)`（`PriceService.java:142`）和 `PricingSkuRequest`（`pricing/dto/PricingSkuRequest.java:22-38`）都没有市场参数；给 `ProductContextDto`/`PricingSkuRequest` 加 `MarketContext` 字段，`PriceStrategy` 内部按 market 取基准价，促销计算逻辑不动。

### 3.4 订单快照：为什么大厂的订单"看不到"商品表

Amazon 订单 API 返回的 `OrderItem` 自带 `Title`、`ItemPrice{Amount, CurrencyCode}`、`ItemTax` [R8]，**不是**让你拿 ASIN 再去查目录。原因：

1. 商品后续改名/改翻译不能改变用户当时看到的东西（法律和客服都需要）。
2. 汇率、税率是时点值，不可重算。
3. 跨服务查目录会把订单可用性绑在商品服务上。

本仓库 `OrderItem` 已有 `productName/description/productInfo/price`（`order/entity/OrderItem.java:71-82`）——快照意识是有的，缺的是坐标：

```text
+ market_code, locale, currency_code       这笔交易的坐标
+ catalog_version, translation_version     指向商品/翻译的哪个版本（可追溯）
+ tax_amount, tax_included                 税
+ erp_product_name                         ERP 需要中文名时单独存，不要覆盖用户看到的名称
```

最后一条来自真实约束：`StartProductHandler.java:195` 的 ERP 同步写死 `setChargeCurrency("人民币")`，并且工厂需要中文品名。用户看英文、工厂看中文，两个名字都要保留。

### 3.5 部署形态的演进路径

```text
现在：  bj 部署 (CN 市场, zh-CN)        rf 部署 (US 市场, en)        ← 两套库、商品各建一次
                     │
第一步：市场和 Locale 变成数据维度，但仍可两套部署（各部署默认不同 MarketContext）
                     │
第二步：同一套服务同时服务多市场，部署只决定默认值；商品一次建、多市场发布
```

第一步到第二步之间最大的工程障碍不是商品，而是**用户体系、支付通道、对象存储区域**（TOS 在 ap-southeast-1 vs 国内）和**数据合规**（GDPR 要求欧盟用户数据不出境）。所以大厂即便商品模型是全局的，物理部署也常按区域分（Amazon 的 NA/EU/FE 三个 region），商品主数据通过复制同步。这一点 Lazada 的"站点独立"并不是没想到全局模型，而是合规和运营先决。

## 4. 搜索与缓存读模型（深入）

### 4.1 ES 多语言的三种策略

| 策略 | 结构 | analyzer | 优点 | 缺点 | 谁在用 |
|---|---|---|---|---|---|
| ① 一文档多字段 | `name_zh / name_en / name_ja` 在同一 doc | 每字段各自 analyzer | 一份索引、一次写 | 字段随语言增长；mapping 爆炸；查询要知道查哪个字段；无法按 locale 过滤"已发布" | 小规模多语言站 |
| ② 按语言分索引 | `product_zh / product_en` | 索引级 analyzer | analyzer 隔离最彻底；可按语言独立调参/扩容 | 跨语言聚合要 multi-index；运维 ×N | 大厂主流（Amazon 按 marketplace 独立） |
| ③ 一 locale 一文档 | `docId = productId#market#locale`，同索引 | 字段用 `fields` 多子字段或按 `locale` 路由到不同 analyzer | 一份索引、按 `locale` term 过滤天然隔离、可按 locale 标发布状态 | 文档数 ×locale 数；同一字段多 analyzer 要靠子字段 | 中等规模的推荐起点 |

ES 官方指南 "Dealing with Human Language" 一章专门讨论了这三种策略（One Language per Document / per Field / Mixed-Language Fields）[R19]，核心警告只有一句：**不要把多种语言塞进同一个用同一 analyzer 的字段**——`ik_max_word` 分英文是逐词切、分日文基本是乱切，召回和打分会互相污染。

本仓库 `ProductIndex.java:36-40` 的 `productName/description` 都是 `ik_max_word`，`ProductIndex.json` 同。只有中文时没问题，一旦写入英文商品，"ring" 会被当成一个 term 还好，但 "sterling silver ring" 的相关性打分和中文商品不在一个尺度。

### 4.2 推荐：策略 ③ 起步，预留切到 ②

```text
索引 trade_product_v2 (通过 alias trade_product_read / trade_product_write 切换)

docId = {productId}#{marketCode}#{locale}
{
  productId, spuId, categoryId, productType, status, ...   ← 身份与通用字段，与 v1 相同
  marketCode, regionCode, locale,                          ← 分区键
  saleStatus, currencyCode, priceMin, priceMax,            ← 该市场的报价摘要（来自 ProductRegion + sku_market_price）
  productName, description,                                ← 该 locale 的内容
  attrOptionIds: [1703, 2201],                             ← 编码化属性，用于 terms 筛选，语言无关
  contentVersion, offerVersion                             ← 幂等与对账
}
```

字段 analyzer 用 mapping 的 `fields` 子字段分语言：

```json
"productName": {
  "type": "text",
  "fields": {
    "zh":      { "type": "text", "analyzer": "ik_max_word" },
    "en":      { "type": "text", "analyzer": "english" },
    "ja":      { "type": "text", "analyzer": "kuromoji" },
    "keyword": { "type": "keyword", "ignore_above": 256 }
  }
}
```

查询时由 `locale` 决定查哪个子字段：`en-US → productName.en`，并且 `must(term locale=en-US) must(term marketCode=US) must(term saleStatus=1)`。这就把 `ProductIndexService.java:261` 的 `matchQuery("productName", searchWord)` 升级为：

```java
String lang = Locale.forLanguageTag(ctx.getLocale()).getLanguage();   // en
String field = "productName." + (SUPPORTED_ANALYZER_LANGS.contains(lang) ? lang : "zh");
baseQuery = QueryBuilders.boolQuery()
        .must(baseQuery)
        .must(QueryBuilders.termQuery("marketCode", ctx.getMarketCode()))
        .must(QueryBuilders.termQuery("locale", ctx.getLocale()))
        .must(QueryBuilders.matchQuery(field, searchWord));
```

**什么时候切到策略 ②**：当某个语言需要独立的同义词/停用词/分词插件调优、或单索引文档数 > 数千万、或不同市场要独立扩缩容时。alias 已经把切换成本降到最低。

### 4.3 同步链路：DTS 行变更 vs 业务事件

本仓库现在是 **DTS（Kafka binlog）→ `trade-order-job` → ES**，监听四张表（`DtsTableAndEsIndex.java:9-12`：product / ext / creator / metric）。这条链路有一个隐含假设：**一行 DB 变更 = 一个 ES 文档变更**。国际化后这个假设破了：

- `trade_pd_product_language` 一行发布 → 只影响 `productId#*#en-US` 这些文档
- `trade_pd_product_region` 一行下架 → 影响 `productId#US#*`
- `trade_pd_attribute_option_i18n` 一行改名 → 影响**所有引用该 option 的商品**在该 locale 的文档（扇出可能上万）

大厂的做法是 **DTS 保底 + 业务事件表达语义**（分别对应 microservices.io 的 Transaction log tailing 与 Transactional outbox 两个模式 [R21]）：

```text
写事务：Product/ProductLanguage/ProductRegion + outbox(event_type, aggregate_id, payload, version)
         │
         ├─ RocketMQ 投递  ProductContentPublished{productId, locale, version}
         │                 ProductOfferChanged{productId, marketCode, version}
         │                 AttributeOptionI18nChanged{optionId, locale}  ← 消费者展开为受影响商品列表，分批重建
         │
         └─ DTS 仍然监听主表，作为"漏事件"的兜底对账
```

消费者幂等靠 `contentVersion/offerVersion`：ES 写入用 `version_type=external` [R20]，旧版本事件直接丢弃。重建任务挂在 xxl-job，按 `(marketCode, locale)` 分片。

### 4.4 缓存 key：维度爆炸与失效粒度

`RedisKey.java:187` 预留的 `product:region:%s:language:%s:detail:` 说明设计者早就想到了。但要注意**维度乘积**：

```text
key 维度 = productId × market × locale × currency × channel
```

5 个市场 × 4 个 locale × 2 个币种 × 3 个渠道 = 120 份详情缓存/商品。大厂的做法是**分层缓存**，不把所有维度揉进一个大 value：

| 缓存层 | key | 变化频率 | TTL |
|---|---|---|---|
| 身份+内容 | `product:content:v2:{productId}:{resolvedLocale}` | 发布时 | 长（30min）+ 事件失效 |
| 报价 | `product:offer:v2:{productId}:{market}` | 改价/上下架 | 中（5min）+ 事件失效 |
| 库存 | 沿用库存服务 | 高频 | 短或实时 |
| 用户相关（促销/定价） | 沿用 `Pricing.PRODUCT_PRICING_CACHE` 按 userId | 高频 | 短 |

详情响应在应用层组装，这样"改一个英文标题"只失效 1 个 content key，而不是 120 个。整体仍是 Cache-Aside 模式 [R22]：读未命中回源并写缓存，写数据后删缓存（先更新 DB 再删 key，顺序不能反）。`resolvedLocale` 用回退后的值而不是请求值，`en-GB` 和 `en-US` 都回退到 `en` 时共享一份。

失效入口：`ProductWriteServiceImpl.deleteRedisKey()`（`ProductWriteServiceImpl.java:315-320`）目前删的是模型列表类 key，国际化后新增按 `(productId, locale)` / `(productId, market)` 的精确失效，由上面的事件消费者触发，不要在写服务里同步删——写服务不知道有多少 locale。

## 5. 翻译工作流与发布（深入）

### 5.1 大厂的翻译不是"调一次翻译 API"

AliExpress、Amazon、Shopee 的共同点是把翻译当作**商品发布流程中的一个有状态环节**，背后通常有一套 TMS（Translation Management System）思想（行业交换格式是 XLIFF [R5]，了解它就能理解 TM/术语表/片段这些概念的来历）：

| 组件 | 作用 | 对本仓库的启示 |
|---|---|---|
| 电商领域机翻模型 | 通用翻译把"吊坠"翻成 "pendant" 还是 "drop" 不稳定；电商模型用商品语料训练 | 翻译供应商做成适配器接口，别把 SDK 写进领域层 |
| 翻译记忆（TM） | 同一句源文（"925 纯银，防过敏"）翻过一次就复用，保证全站一致、省钱 | 第一阶段可以用 `content_hash` 做最简 TM：源 hash 相同直接复用译文 |
| 术语表（Glossary） | 品牌名、材质名强制翻法 | Nacos 维护一份 `glossary`，机翻后做替换校验 |
| 人工审核队列 | 按商品重要度/GMV 排优先级 | 复用现有 `trade_pd_product_audit_history` 的审核思路 |
| 源变更检测 | 源语言改了，所有译文标 STALE，线上保留旧版 | 这是整个工作流里最容易漏、漏了最难查的一环 |

### 5.2 状态机与版本模型

每个 `(productId, locale, regionCode)` 一条内容行，状态机：

```text
                 源内容变更
                 ┌────────────────────────────────────────┐
                 ▼                                        │
  SOURCE ──► MACHINE_TRANSLATED ──► HUMAN_REVIEWING ──► APPROVED ──► PUBLISHED ──► STALE
   (源语言)         │                      │                               ▲         │
                    │                      └──► REJECTED ──► (重新机翻/人工) │         │
                    │                                                      │         │
                    └──────────── 人工直接编辑 ─────────────────────────────┘   重翻后发布新版本
```

版本模型用**两个版本号 + 一个 hash**：

```text
source_version   源语言内容的版本（zh-CN 行每次保存 +1）
version          本语言行自己的版本（乐观锁）
content_hash     本行文本的 hash，用于 TM 复用和"内容没变就别重发事件"
translated_from_source_version   本译文基于源的哪个版本 → 小于当前 source_version 即 STALE
```

关键规则（对应 AliExpress 的"人工覆盖不被机翻冲掉"）：

1. `translation_source = HUMAN` 的行，机翻任务**只标 STALE 不覆写**，等人工处理。
2. `translation_source = MACHINE` 且未发布的行，源变更后可以直接重翻覆盖。
3. 发布是**整行原子切换**：`PUBLISHED` 行永远只有一条（唯一键保证），新版本审核通过后在一个事务里把旧行置 `ARCHIVED`、新行置 `PUBLISHED`、写 outbox。

### 5.3 质量门禁：机翻结果为什么要校验

机翻会破坏的东西，大厂都有自动校验：

| 检查项 | 失败示例 | 校验方式 |
|---|---|---|
| 占位符 | 源 `「{0}」已发货` → 译文丢了 `{0}` | 正则抽取占位符集合，源译相等 |
| HTML 结构 | 详情里的 `<img>`、`<p>` 被翻译/删除 | 翻译前抽出标签占位，翻译后还原；或 DOM diff |
| 长度 | 标题超过 ES/前端限制 | 按 locale 配置上限（日文/德文通常更长） |
| 术语 | "925 银" 被翻成 "925 money" | Glossary 强制替换 + 禁词表 |
| 数字/单位/货币 | "18K" 变 "18 k"、"¥" 残留 | 单位白名单；货币符号一律由前端按 currency 渲染，文本里不出现 |
| 合规 | 珠宝材质、过敏、尺寸、税费描述 | 这些字段**必须人审**，不允许 MACHINE 直接 PUBLISHED |

本仓库现在 `i18n/messages_zh.properties` 里的 push 文案 `「{0}」已进入制作阶段` 正是占位符例子。

京东公开的两条经验可以直接借鉴：一是"先查公共词条库、查不到再机翻、机翻后人工校对"的顺序 [R24]，对应上表的 TM 和人审；二是用大模型做翻译质检并以**采纳率**作为质检本身的质量指标（他们从 11% 调到 85.71%）[R23]——质检工具自己也要被度量，否则会变成噪音。

### 5.4 本仓库落点

**表**：`ProductLanguage` 补字段（落地版 4.1 已给 DDL），`ProductDraft` 已有 `regionCode + languageCode`（`ProductDraft.java:47-52`），直接作为翻译草稿，不用新建草稿表。

**接口**（沿用 `/inner/product` 风格，`ProductInnerController`）：

```http
PUT  /inner/product/{productId}/i18n/{locale}            保存草稿（version 乐观锁）
POST /inner/product/{productId}/i18n/{locale}/translate  触发机翻（异步，返回任务 id）
POST /inner/product/{productId}/i18n/{locale}/submit     提交审核
POST /inner/product/{productId}/i18n/{locale}/publish    发布（幂等：同 version 重复发布返回成功）
GET  /inner/product/{productId}/i18n                     各 locale 状态总览（含 STALE）
```

**翻译适配器**：

```java
package cn.mathmagic.jjewelry.business.productdomain.i18n.translate;

import java.util.List;

/** 翻译供应商抽象。领域层只依赖此接口；具体厂商（阿里翻译/DeepL/自建）在 infra 层实现。 */
public interface TranslationProvider {

    /**
     * 批量翻译，供应商侧通常按字符计费且有并发限制——调用方按商品攒批，不要逐字段调用。
     * @param segments 待翻译片段（已把 HTML 标签和占位符抽成 token）
     */
    List<TranslatedSegment> translate(String sourceLocale, String targetLocale, List<SourceSegment> segments);
}
```

**任务**：机翻是异步的，用 RocketMQ `ProductTranslateRequested` 事件 + 消费者调用 `TranslationProvider`，结果写回 `MACHINE_TRANSLATED`。消费者是子线程语义，**不要读 `AuthContext`**，操作人从事件 payload 里带。

## 附录：术语表

| 术语 | 释义 |
|---|---|
| SPU / SKU | 标准产品单元 / 库存量单位；SKU 由 SPU + 销售属性组合确定 |
| CPV | Category-Property-Value，淘宝商品中心的类目-属性-值模型 [R10] |
| Locale | 语言 + 可选脚本 + 可选地区，BCP 47 形式 [R1]，如 `zh-Hans-CN` |
| Market / Marketplace | 销售市场；决定可售、价格、币种、税、合规 |
| Venture | Lazada 对国家站点的称呼 |
| Offer | 某商品在某市场的报价（价格 + 可售 + 物流 + 税），Amazon 术语 |
| Listing | 某商品在某站点的完整展示 + 报价，Amazon/Lazada 术语 |
| BIL | Build International Listings，Amazon 跨市场同步工具 [R9] |
| GSP / SIP | Shopee 全球商品平台 / 跨境自动派生平台 [R17] |
| TMS / TM / Glossary | 翻译管理系统 / 翻译记忆 / 术语表（交换格式 XLIFF [R5]） |
| STALE | 源内容已变更、译文过期但线上仍在用旧版的状态 |
| Outbox | 与业务数据同事务写入的事件表，异步投递保证不丢事件 [R21] |
| Cache Aside | 读缓存未命中回源并写缓存、写数据后失效缓存的模式 [R22] |
