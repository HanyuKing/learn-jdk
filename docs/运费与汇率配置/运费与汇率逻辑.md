# Builda 运费与汇率逻辑

本文只写 Builda。商品金额按美元汇率换算；运费不乘这套汇率，按收货国家和结算币种从配送配置里直接取价。汇率和运费价表都在 Nacos。订单只保存换算后的金额、选中的运费金额、币种和配送档位 code，不保存汇率本身。

租户来自当前请求的 `AuthContext`。解析后等于 `TENANT_BUILDA` 才走下面的换汇和配送档位。判断方法是 `CheckoutDeliveryService.isBuildaCheckoutDelivery()`。

## 1. 存在哪

### 1.1 汇率配置

Nacos group `order`，dataId `order-common.json`，字段 `usdExchangeRate`。读取类 `NacosOrderCommonConfig`，换算类 `UsdExchangeRateService`。

键是小写货币代码，值是字符串，表示 1 美元等于多少目标货币。不配置 `usd`。值用字符串是为了避免按 double 解析。

```json
{
  "usdExchangeRate": {
    "jpy": "150"
  },
  "minAmount": {
    "USD": 0.5,
    "JPY": 50
  }
}
```

同一份配置里的 `minAmount` 是各币种最低交易额。非美元结账必须能取到该币种的正数，否则结账失败，不会用美元的 0.5 兜底。美元仍走原来的最低额。

### 1.2 运费配置

Nacos group `order`，dataId `builda-checkout-delivery.json`。类是 `BuildaCheckoutDeliveryRootConfig`。配置空或无效时 `resolveEffective()` 抛错，结账失败。运行时不读 classpath 里的示例 JSON。

```text
destinations.{国家ISO2}.methods[]
destinations.{国家ISO2}.regionOverrides.{省/州}.methods[]
fallbackPolicy.allowCheckout
fallbackPolicy.methods[]
```

每个档位：

| 字段 | 含义 |
| --- | --- |
| `code` | 档位编码，下单回传，写入订单扩展 |
| `feesByCurrency` | 大写 ISO 4217 到金额。这就是该档在该币种下的运费 |
| `name` / `etaText` | 单语文案兜底 |
| `nameI18n` / `etaTextI18n` | 按 `Accept-Language` 选文案，对不上再退 `en-US` |
| `default` | 是否默认选中，只给展示 |

### 1.3 订单上留下什么

| 位置 | 内容 |
| --- | --- |
| `trade_order.currency` | 小写结算币种，`usd` 或 `jpy`。与单价、运费、应付同一套单位 |
| `trade_order_item.price` | 换汇后的单价 |
| `trade_order.shipping_fee` | 创单时选定档位的运费金额 |
| `trade_order.total_amount` | 换汇后的商品总额 + `shipping_fee`。还没扣优惠 |
| `trade_order.discount_amount` | 换汇后的活动优惠 |
| `trade_order.promo_code_discount_amount` | 优惠码减免。立减、一口价已按同一汇率换过；不用码时为空 |
| `trade_order.pay_amount` | 商品总额 + 运费 − 活动优惠 − 优惠码，再进入后续计税。运费留在应付里 |
| `trade_order_ext.extend.shippingMethodCode` | 档位 code。运费金额不写在 extend 里 |

汇率数字、`feesByCurrency` 整张表、省州覆盖规则都不落库。改 Nacos 只影响之后的算价，已创建订单的单价和运费不变。

## 2. 汇率怎么算

商品和活动优惠在库里按美元存。请求币种来自请求头 `Currency`。`CurrencyEnum` 目前只有 `usd`（2 位小数）和 `jpy`（0 位小数）。code 必须小写，方法 `CurrencyEnum.of` 不把大写转成小写。

`UsdExchangeRateService.resolve`：

1. 空白当美元，汇率为空，金额保持原价。
2. 不是三位小写字母，直接拒绝。
3. 小写但不在 `CurrencyEnum` 里，退回美元。
4. 是 `jpy` 但 `usdExchangeRate` 没有这个键、值为空、不是正数，退回美元。
5. 否则 `rate` 为配置值，`converted = true`。

换算：

```text
目标金额 = 美元金额 × rate，按该币种小数位 HALF_UP
商品总额 = 换算后的单价 × quantity，再按小数位 HALF_UP
```

先换单价再乘数量，避免总价单独四舍五入后和单价对不上。美元不乘。

同一次 `rate` 用在：

- SKU 单价、商品总额
- 活动优惠。换算后大于换算后的商品总额时，截到商品总额
- 优惠码的立减、一口价配置值。百分比是应付比例，不乘汇率，直接打在已经换汇的商品金额上

运费不乘 `usdExchangeRate`。

活动优惠换算后变成 0 时，预下单会清掉渠道、券和活动 ID，避免用户没少付钱、券却被冻住。

优惠码封顶只看商品：可减空间是「换汇后的商品总额 − 活动优惠 − 该币种最低交易额」。运费不参与这个下限。

## 3. 运费怎么算

结账运费是订单上一笔固定金额，不乘购买数量，也不乘美元汇率。金额来自命中档位的 `feesByCurrency`。

查询接口：`GET /checkout/shipping-options?addressId=`，币种用请求头 `Currency`，空则 USD。

取价步骤（`CheckoutDeliveryConfigService`）：

1. 地址必须属于当前用户。用地址上的 `countryCode`、`province`。国家、省/州转大写，省可空。国家为空则失败。
2. 请求币种空白当 USD，再转成大写去对 `feesByCurrency`。
3. 在 `destinations` 里按国家找配置，key 忽略大小写。省/州命中 `regionOverrides` 且覆盖里有档位时，用覆盖档位；否则用该国家的默认档位。
4. 国家没有配置，或档位为空，走 `fallbackPolicy`。`allowCheckout = false` 时报国家不支持。fallback 自己也没有档位则配置非法。
5. 用请求的 `shippingMethodCode` 精确匹配档位。对不上则失败。`/price/compute` 和创单在已有地址但没传档位时也会失败。
6. 该档有请求币种就用该金额。没有则金额退回 USD，并打 warn。USD 也没有则配置非法。
7. 配送选项接口里，全部档位都有请求币种时，返回币种用请求币种；否则整单返回币种退到第一档能解析出的币种，通常是 USD。

展示：金额为 0 或空时卡片右侧是 `FREE`，否则是 `+` 加货币符号加金额。日元不带小数，美元保留两位。

商品上的运费模板（`freight_template`、`trade_pd_product.freight_template_id`）会先被价格策略算一遍。Builda 结账在换汇之后执行 `clearTemplateShipping`，把这笔模板运费清掉，再写入上面的档位价。模板匹配规则不决定 Builda 结账运费。

商详上的 `shippingFee` 仍是模板运费，且换汇时不改这个字段。它不是结账页的档位价。

## 4. 结账时怎么拼在一起

`PriceService.getPrice` 在 Builda 下的顺序：

1. 价格策略按 SKU 美元原价和运费模板先出一版价格。
2. `resolve(请求币种)` 得到汇率，`applyPrice` 换单价、商品总额、活动优惠，并写下 `price.currency`。
3. 清掉模板运费、`totalPrice`、`payPrice`。
4. 地址为空：运费记 0。地址有值：用请求币种（不是第 2 步退回后的币种）去 `feesByCurrency` 取档位价。
5. 优惠码用第 2 步的汇率和最低交易额，只减商品。
6. 写回：

```text
shippingFee = 档位配置价
totalPrice  = productTotalPrice + shippingFee
payPrice    = max(0, totalPrice − activityDiscount − promoDiscount)
```

预下单 `PreOrderService.getPreOrderHasAddressId`：先按模板算出运费并换商品金额，再 `applyBuildaSettlementCurrency` 把币种设成请求币种的小写形式。只有地址和档位都有时，才调用同一次 `getPrice` 覆盖商品总额、运费、总价、应付、活动优惠和币种。缺地址或缺档位时不覆盖，页面上仍可能是模板运费。

创单会再调一次 `getPrice`，并把结果写入订单。`shipping_fee` 来自这次报价。明细单价来自同一次请求里预下单已经换好的 `price`，使用的是同一个请求币种。`resolveOrderCurrency` 取的是这次报价上的 `currency`：请求头是 `jpy` 但汇率退回美元时，订单币种是 `usd`。

两条回退互不影响：

- 汇率缺失：商品金额保持美元，`price.currency` 变成 `usd`。
- `feesByCurrency` 没有请求币种：运费金额改用 USD 那一档的数字。`getConfiguredShippingFee` 不会因此改写商品币种。

因此「有日元汇率、但运费没配 JPY」时，商品是日元，运费是配置里的美元数字，两者直接相加。配送选项接口遇到这种情况会把返回币种标成 USD；算价接口仍把这个美元数字加进当前 `payPrice`。

## 5. 各入口

| 入口 | 商品金额 | 运费 |
| --- | --- | --- |
| 商详 | 按请求币种乘 `usdExchangeRate` | 模板运费，不乘汇率，也不是配送档位 |
| `GET /checkout/shipping-options` | 不涉及 | 按国家和省/州列出档位及 `feesByCurrency` |
| `POST /price/compute` | 乘汇率 | 有地址则取档位价；无地址为 0。无档位且有地址则失败 |
| 预下单 | 乘汇率 | 地址和档位都有才改成档位价 |
| 创单 | 单价用预下单换汇结果；总额用创单当次报价 | `shipping_fee` 为创单当次档位价 |

运费参与应付，不参与优惠和最低交易额。档位价在加优惠之前确定，优惠不会把它改掉。
