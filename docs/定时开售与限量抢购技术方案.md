# 定时开售与限量抢购技术方案

## 1. 文档信息

- **文档状态**：草案
- **适用范围**：定时上架、定时开售、限量抢购、直播间爆款等场景
- **核心目标**：开售时间准确、库存不超卖、流量可削峰、订单可恢复、链路可对账
- **重要说明**：本文对京东、阿里、抖音的描述，来自公开技术分享、论文、专利、事故复盘和行业共性推断，不代表其内部源码或当前全部实现。各业务线和年份可能存在差异。

## 2. 结论摘要

大厂的定时开售通常不是依赖某个定时任务在开售瞬间批量更新商品状态，而是采用以下组合：

```text
服务端时间窗口校验
    + 开售前缓存/库存预热
    + CDN 与动静分离
    + 网关限流、风控、资格校验
    + 原子库存预占
    + MQ 排队削峰
    + 异步创建订单
    + 支付确认或超时释放
    + 库存流水与订单对账
```

建议按流量和库存重要程度分三档建设：

1. **普通定时销售**：数据库条件扣减 + 本地事务，适合峰值可控的商品。
2. **高并发限量销售**：Redis 高速闸门 + MQ 削峰 + 数据库持久化预占，适合秒杀和直播爆款。
3. **极高价值/极少量库存**：热点 SKU 独立队列化或单 SKU 串行处理，宁可少卖，也不能超卖。

如果只选择一个通用落地方案，推荐第二档，但要保留第一档的数据库最终校验和库存流水。

## 3. 先区分两类业务

### 3.1 普通定时上架

商品在指定时间前不可购买，开售后按普通订单流程销售，库存量充足且流量可控。

此时不需要完整的秒杀架构。服务端只需要根据时间窗口判断是否可售，订单服务正常执行库存冻结即可。

### 3.2 定时限量抢购

商品在指定时刻集中开售，库存有限，短时间请求量可能远大于库存量。

此时必须重点处理：

- 瞬时流量洪峰；
- 单 SKU 热点；
- 重复点击和机器人请求；
- 库存预占、支付超时释放；
- MQ 堆积和服务故障恢复；
- Redis、数据库、订单状态之间的最终对账。

本文后续主要讨论第二类，同时兼容第一类。

## 4. 大厂公开方案与行业共性

### 4.1 京东：交易链路隔离与异步削峰

公开分享中反复出现的设计重点包括：

- 商品详情、活动页静态化，尽量由 CDN 承接读流量；
- 开售前预热商品、价格、活动规则和库存；
- 抢购入口与普通下单入口隔离；
- 网关限流、黑名单、验证码或资格校验；
- 库存预占后异步创建订单；
- 支付超时自动释放库存；
- 对热点商品和普通商品进行资源隔离。

**可借鉴点**：零售交易链路清晰，库存预占、订单创建、支付确认的状态边界比较明确。

**代价**：需要建设消息重试、超时释放、库存对账等补偿能力，不能只实现一个“扣库存接口”。

### 4.2 阿里：流量分层、库存前置与单元化

公开技术资料和大促实践中常见的模式包括：

- 页面和静态资源尽可能在边缘或缓存层完成；
- 通过流量分层、资格校验、令牌和队列把无效请求挡在交易系统外；
- 库存提前加载到高速缓存或库存服务；
- 使用消息队列削峰，将瞬时请求转化为稳定消费速率；
- 通过单元化、分区和活动隔离避免全站被单个热点拖垮；
- 全链路压测、容量评估、降级和熔断作为发布前置条件。

**可借鉴点**：不仅优化单个接口，而是从入口、缓存、库存、订单、消息、部署单元进行全链路治理。

**代价**：基础设施和运维体系复杂，适合多个大促活动长期运行的组织，不适合一开始就全部复制。

### 4.3 抖音：突发流量治理与资格/风控前置

抖音电商的流量来自推荐、直播和短视频，流量突发性更强。公开资料和行业实践中常见的方向包括：

- 在边缘和网关层拦截异常流量；
- 通过用户、设备、IP、渠道、预约等维度做资格判断；
- 通过令牌、排队和放量控制保护订单系统；
- 使用独立的库存中心处理预占、确认、释放；
- 使用事件驱动和异步订单降低同步链路压力；
- 对主播、场次、商品和活动进行隔离，避免单个直播间影响全局。

**可借鉴点**：把风控和流量治理放到库存、订单之前，适合不可预测的突发流量。

**代价**：用户可能看到排队或处理中状态，必须设计好结果查询和失败补偿体验。

### 4.4 三家方案的共同骨架

```text
CDN/静态页
    ↓
WAF/网关/风控/限流
    ↓
服务端时间窗口与活动开关
    ↓
资格校验/一次性令牌/排队
    ↓
库存高速预占
    ↓
库存服务持久化预占
    ↓
MQ
    ↓
订单创建
    ↓
支付确认或超时释放
```

关键取舍是：

- **库存必须防超卖**；
- **订单可以排队和异步化**；
- **缓存负责性能，数据库和库存流水负责可追溯性**；
- **活动开售由服务端时间判断，调度任务只负责准备和巡检**。

## 5. 方案对比

| 方案 | 适用场景 | 核心实现 | 一致性 | 吞吐 | 复杂度 |
| --- | --- | --- | --- | --- | --- |
| 数据库条件扣减 | 普通定时销售、峰值可控 | MySQL 条件 UPDATE + 事务 | 强 | 中 | 低 |
| Redis 闸门 + MQ | 秒杀、限量抢购、直播爆款 | Redis 原子预占 + MQ + 数据库落库 | 防超卖，允许短暂排队 | 高 | 中高 |
| 热点 SKU 串行队列 | 极少库存、高价值商品 | 单 SKU 分区队列/Actor | 最强 | 单 SKU 受限 | 中高 |
| 直接设置绝对库存 | 盘点、ERP 全量同步、人工校准 | 带版本的绝对值修正 | 取决于版本控制 | 不适合作为交易路径 | 低 |

## 6. 推荐的领域边界

### 6.1 活动域

负责：

- 销售计划；
- 开售时间和结束时间；
- 活动价格快照；
- 活动库存配额；
- 用户限购规则；
- 活动开关和资格规则。

### 6.2 商品域

负责：

- 商品、SKU、规格和基础售价；
- 商品基础库存的归属；
- 商品是否允许参与活动。

### 6.3 库存域

负责：

- 活动库存分配；
- 库存预占、确认、释放；
- 库存流水；
- 防超卖和库存对账。

### 6.4 交易域

负责：

- 抢购请求幂等；
- 订单创建；
- 支付状态；
- 取消、关闭和售后触发库存释放。

活动域可以配置限购规则，但真正的扣减、预占、累计购买量和并发控制，应由库存域和交易域共同完成。

## 7. 库存模型与数据存储

### 7.1 活动库存独立建模

不建议在开售时直接修改商品主库存状态。建议在活动发布时先从商品库存分配活动额度。

例如商品有 100 件，活动分配 20 件：

```text
商品基础库存：100 -> 80
活动可用额度：  0 -> 20
```

活动期间只操作活动库存：

```text
AVAILABLE -> RESERVED -> SOLD
                     ↘ RELEASED -> AVAILABLE
```

活动结束后，未售出的活动额度通过流水回补商品基础库存。

### 7.2 建议表结构

```text
sale_plan
---------
id, sku_id, start_time, end_time, status,
sale_price, total_quota, per_user_limit, version

sale_stock
----------
sale_id, sku_id, bucket_no,
total_stock, available_stock, reserved_stock, sold_stock, version

stock_reservation
-----------------
reservation_id, request_id, sale_id, sku_id, user_id,
quantity, status, expire_time, created_at, updated_at

stock_ledger
------------
id, biz_id, sale_id, sku_id, user_id,
delta, operation_type, request_id, created_at
```

必须至少保证：

```text
reserved_stock + sold_stock <= total_stock
```

### 7.3 交易更新使用增减量

普通数据库方案可使用条件更新：

```sql
UPDATE sale_stock
SET available_stock = available_stock - :quantity,
    reserved_stock = reserved_stock + :quantity
WHERE sale_id = :saleId
  AND sku_id = :skuId
  AND available_stock >= :quantity;
```

库存扣减、释放、确认均使用增减量，并写入幂等流水。

绝对值只用于盘点、同步和修正，且需要 `version` 或来源时间条件：

```sql
UPDATE sale_stock
SET available_stock = :newValue,
    version = version + 1
WHERE sale_id = :saleId
  AND sku_id = :skuId
  AND version = :expectedVersion;
```

## 8. 高并发方案的请求时序

```text
用户 -> CDN：读取活动页
用户 -> 网关：提交抢购请求
网关 -> 风控：用户/设备/IP/渠道校验
网关 -> 活动服务：校验服务端时间和活动开关
活动服务 -> 令牌服务：获取一次性令牌
令牌服务 -> Redis：原子预占活动库存
Redis --> 用户：返回 requestId，状态为 PROCESSING
库存服务 <- MQ：消费预占命令
库存服务 -> MySQL：幂等写入 reservation + 条件扣减
库存服务 -> MQ：发送可下单事件
订单服务 -> MySQL：创建待支付订单
支付服务 -> 订单服务：支付成功
订单服务 -> 库存服务：确认预占为 SOLD
```

支付超时或订单取消：

```text
订单服务 -> 库存服务：释放 reservation
库存服务 -> MySQL：RESERVED -> AVAILABLE
库存服务 -> Redis：补回高速闸门库存
```

用户在排队期间不能看到“已经抢购成功”，只有库存服务完成持久化预占并且订单创建成功后，才返回最终成功状态。

## 9. Redis 与库存分桶

### 9.1 Redis 的职责

Redis 适合承接：

- 活动元数据缓存；
- 开售时间和活动开关缓存；
- 高速库存闸门；
- 用户重复请求快速拦截；
- 资格和令牌；
- 短期排队状态。

Redis 不应成为唯一的最终库存事实，数据库库存和库存流水必须能够恢复和对账。

### 9.2 库存分桶

单个热点 SKU 可以拆成多个库存桶：

```text
sale:{saleId}:{skuId}:stock:0
sale:{saleId}:{skuId}:stock:1
sale:{saleId}:{skuId}:stock:2
...
```

桶数量根据压测确定，不宜盲目增大。随机分桶可能导致局部桶耗尽，因此需要多桶重试、剩余量感知或预生成库存令牌。

如果使用 Redis Cluster，Lua 脚本涉及的 Key 必须通过相同 hash tag 放入同一个 slot，否则不能保证跨 Key 原子性。

## 10. 调度与开售时间

### 10.1 服务端时间是真相

每次购买请求必须判断：

```text
serverNow >= startTime
&& serverNow < endTime
&& saleStatus != DISABLED
```

客户端倒计时只能用于展示，不能作为购买资格依据。服务端统一使用 UTC 或带时区的时间类型，避免多机时区和夏令时问题。

### 10.2 调度任务只做辅助工作

建议将任务拆为：

- `T-30m`：生成不可变的活动快照；
- `T-10m`：预热活动信息、价格和库存；
- `T-1m`：开启风控、限流和压测探针；
- `T`：进入开售窗口；
- `T+`：持续消费队列、处理订单；
- `endTime`：停止新请求；
- 活动结束后：释放未支付预占、回补未售额度、执行对账。

不要为每个活动创建独立线程定时器。可以使用延迟消息、Redis ZSet、Quartz/XXL-JOB 分片或按时间片扫描。任务必须幂等、可重试，并通过补偿扫描兜底漏执行。

## 11. 幂等、限购与防超卖

### 11.1 请求幂等

客户端每次抢购生成 `request_id`，服务端建立：

```text
UNIQUE(request_id)
```

消息重试、HTTP 重试和消费者重启都不能重复预占库存。

### 11.2 用户限购

限购判断应为：

```text
已购买数量 + 已预占数量 + 本次数量 <= 限购数量
```

高并发时可先用 Redis 或 Bloom/Cuckoo Filter 做快速拦截，数据库唯一约束和用户购买累计表做最终兜底。

### 11.3 防超卖

Redis 预占成功不等于最终成功。库存服务落库时仍需要条件更新和唯一约束：

```text
reservation(request_id) 不存在
且 available_stock >= quantity
```

落库失败时，预占令牌必须在 TTL 到期后或通过补偿消息释放，不能永久吞掉库存。

## 12. 消息、事务与故障恢复

### 12.1 Outbox

库存预占和订单命令需要可靠发送。建议在数据库事务中写入 Outbox：

```text
库存预占 + reservation记录 + outbox事件
```

事务提交后由后台转发 MQ，发送失败自动重试。

### 12.2 超时释放

支付超时释放不能只依赖定时任务，建议组合使用：

- 延迟消息快速释放；
- 定时扫描兜底；
- 释放操作幂等；
- Redis 和数据库同时补偿。

### 12.3 Redis 或 MQ 故障

限量抢购在无法确认库存时建议失败关闭：

- 暂停发放令牌；
- 返回“系统繁忙，请稍后再试”；
- 保留已持久化的预占继续处理；
- 恢复后执行 Redis、数据库和库存流水对账。

宁可短时间少卖，也不要在库存状态不确定时继续放行。

## 13. 存储与部署建议

### 13.1 数据库

- 活动计划和库存配置可以按活动维度查询；
- 预占表按活动、创建日期或业务分片；
- 高频查询使用游标分页，不使用大 `OFFSET`；
- `request_id`、`reservation_id`、`sale_id + user_id + sku_id` 建立唯一或组合索引；
- 热点库存按 `sale_id + sku_id + bucket_no` 分桶，减少单行锁竞争。

### 13.2 Redis

- 活动信息和价格做版本化缓存；
- 库存预热要有校验和；
- 主从、哨兵或集群模式根据可用性要求选择；
- 设置预占 TTL，避免异常请求永久占库存；
- 缓存重建不能直接从不一致的订单结果推导库存，应以库存流水和数据库为准。

### 13.3 MQ

- 活动或热点 SKU 可以独立 Topic/分区；
- 消费能力按数据库和订单服务真实处理能力配置；
- 监控消费延迟、积压、重试和死信；
- 订单创建消费者必须幂等。

## 14. 监控、压测与运营开关

必须监控：

- 开售请求量、有效请求量、拦截量；
- 令牌发放量和 Redis 预占成功量；
- 数据库预占成功量；
- MQ 堆积和消费延迟；
- 订单创建 P95/P99；
- 支付超时和库存释放量；
- Redis、数据库、库存流水差异；
- 重复请求、异常设备和风控命中率。

必须提供：

- 关闭活动；
- 关闭单个 SKU；
- 降低放量速率；
- 暂停订单创建；
- 暂停支付；
- 只读展示；
- 启动库存对账和人工补偿。

上线前至少进行：

1. 开售瞬时洪峰压测；
2. 单 SKU 热点压测；
3. Redis 主从切换演练；
4. MQ 延迟和重复投递演练；
5. 数据库故障和订单服务降级演练；
6. 支付超时、取消和重复回调演练。

## 15. 分阶段落地计划

### 阶段一：先满足普通定时开售

实现：

- `sale_plan` 和活动库存表；
- 服务端时间窗口校验；
- 数据库条件扣减；
- 预占、支付确认、超时释放状态机；
- 请求幂等和库存流水；
- Outbox 消息可靠发送。

### 阶段二：应对高并发

增加：

- CDN 和页面静态化；
- Redis 活动信息和库存预热；
- 网关限流、风控和资格校验；
- Redis 原子闸门；
- MQ 排队和异步订单创建；
- 活动级资源隔离。

### 阶段三：治理热点商品

增加：

- 库存分桶；
- 热点 SKU 独立队列或分区；
- 独立容量、压测和熔断开关；
- 更细粒度的用户、设备、IP 风控；
- 自动对账、库存重放和异常工单。

## 16. 最终推荐

对于珠宝电商系统，推荐采用以下默认架构：

```text
活动域保存销售计划、价格快照和限购规则
商品域保存商品与基础库存
库存域维护活动库存、预占、确认、释放和流水
交易域维护请求幂等、订单和支付状态

开售前：快照与预热
开售时：服务端时间校验 + 网关限流 + Redis原子闸门
开售后：库存持久化预占 + MQ削峰 + 异步创建订单
支付成功：预占转已售
支付超时：预占释放并回补
活动结束：未售额度回补商品库存并完成对账
```

关键原则：

1. 定时任务负责准备和巡检，不负责决定用户能否购买。
2. 活动库存独立建模，通过库存转移流水与商品基础库存衔接。
3. 交易过程使用增减量，绝对值只用于带版本的盘点和校准。
4. Redis 负责性能和快速拦截，数据库与库存流水负责最终事实。
5. 订单可以异步，库存预占必须有明确的持久化和补偿边界。
6. 所有扣减、释放、确认、回补都必须幂等。
7. 高并发场景优先保证不超卖，允许排队和少量少卖。
8. 只有真正的热点 SKU 才启用更重的分桶和串行化方案。

## 17. 待确认参数

正式实施前需要根据实际业务补充以下参数：

- 单个活动预计峰值请求量和持续时间；
- 单个热点 SKU 的库存量；
- 用户是否允许一次购买多件；
- 未支付订单的锁库存时长；
- 是否允许活动库存和普通库存混卖；
- 支付失败、取消订单后的库存回补规则；
- 是否允许预售、预约、排队结果异步通知；
- 数据库、Redis、MQ 的现有部署规模和可用性要求。
