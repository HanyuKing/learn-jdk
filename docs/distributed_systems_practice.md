# 分布式系统实践与项目验收手册

> 实践主线采用 MIT 6.824（现为 6.5840 Distributed Systems）的 Go 实验。课程版本会变化，开始前从[课程主页](https://pdos.csail.mit.edu/6.824/)选择一个完整学期，固定该版本的实验说明、代码框架和测试；不要混用不同年份的接口。

## 1. 实践总原则

### 1.1 课程实验与扩展项目的分工

- **6.5840/6.824**：训练分布式算法、故障模型、状态机和正确性思维；按原版 Go 完成。
- **扩展项目**：训练生产工程能力，例如配置、持久化格式、指标、部署、升级、消息幂等和运维；可用 Java 或 Go。
- **论文复现**：选择少量核心机制进行可控复现，重点验证论文假设和代价，不追求复刻生产规模。

### 1.2 通用提交物

每个实验或项目必须保留：

1. 设计文档：系统模型、API、状态机、持久化边界和关键不变量。
2. 测试日志：命令、版本、测试数量、耗时、失败样本和重试次数。
3. 故障报告：注入的故障、观察到的事件顺序、根因、修复和回归测试。
4. 性能报告：吞吐、P50/P95/P99、恢复时间、CPU/内存/磁盘/网络占用。
5. 复盘记录：一个原设计中的错误假设，以及它怎样被测试暴露。

### 2.1 基础工具

- 能用 WAL、fsync、检查点和恢复日志解释一个进程崩溃后的数据状态。
- 能构造一个 RPC 响应丢失导致客户端重试的重复执行例子。
- 能阅读课程测试代码，区分测试验证的是安全性还是活性。

## 3. MIT 6.5840/6.824 实验主线

### Lab 1：MapReduce

**核心能力**

- Coordinator/Worker 的任务生命周期、超时回收和重新分配。
- 并发进程之间的 RPC、临时文件和原子提交。
- Worker 崩溃时如何避免丢失或重复最终输出。

**实现检查点**

- 任务状态至少区分 Idle、Running、Finished，并记录开始时间和尝试编号。
- 输出写入临时文件，完成后使用原子 rename，避免半成品被下游读取。
- Coordinator 的等待和清理逻辑可安全重复执行，不能因一个 Worker 永久挂起。
- 处理输入为空、Map/Reduce 数量不一致、Worker 先退出和任务重复完成。

**额外故障测试**

- 随机杀死 Worker、延迟 RPC、丢弃响应、让 Worker 只完成部分输出。
- 检查最终输出集合是否正确、是否存在半文件、是否发生不可解释的数据重复。

**验收**

- 课程官方测试全部通过。
- 连续运行 100 次随机 Worker 故障测试，无数据错误。
- 能解释“任务执行多次”与“最终输出只提交一次”的差异。

### Lab 2：Raft

建议按课程提供的子阶段逐步提交：领导者选举与心跳、日志复制、持久化、快照/日志压缩。

**必须写下的不变量**

1. Election Safety：一个任期最多一个 Leader。
2. Leader Append-Only：Leader 不覆盖或删除自己的日志。
3. Log Matching：相同 index 和 term 的日志项内容相同，前缀相同则前缀一致。
4. Leader Completeness：已提交的日志项会出现在更高任期的 Leader 中。
5. State Machine Safety：不同节点不会在同一 index 应用不同命令。

**关键故障矩阵**

| 场景 | 必须观察 |
| --- | --- |
| 旧 Leader 与多数派断开 | 旧 Leader 不能提交新日志；多数派可选出新 Leader |
| 新 Leader 尚未复制完整日志即崩溃 | 后续 Leader 不能丢失已提交项 |
| 网络恢复且日志冲突 | Follower 冲突后回退到匹配前缀，再复制 Leader 日志 |
| 节点写入日志后、回复前崩溃 | 重启后日志可恢复，客户端重试不破坏状态机 |
| Snapshot 传输中断 | 节点可以重试，不能应用截断或不完整快照 |
| 反复选举和高并发提交 | 无活锁；提交延迟和消息量保持在可解释范围 |

**工程要求**

- 持久化 `currentTerm`、`votedFor` 和日志的边界要明确；回复客户端前判断何时必须落盘。
- 所有定时器重置都有理由，避免无条件重置导致选举活性下降。
- ApplyCh 不能因为慢消费者阻塞 Raft 的网络处理；需要说明背压策略。
- Snapshot 必须同时处理 Raft 日志截断和上层状态机快照。

**验收**

- 课程测试全部通过，并连续运行长时间随机网络测试。
- `go test -race` 无竞态；不能使用 sleep 作为正确性同步手段。
- 提交一份状态转换图，说明每类 RPC 在每种任期关系下如何处理。
- 完成一次 Raft 设计答辩：解释为何某个实现满足五个不变量。

### Lab 3：基于 Raft 的容错 KV 服务

**核心能力**

- 将应用命令封装为 Raft 日志，等待对应 index/term 的提交结果。
- 客户端请求去重和 Leader 变化后的重试。
- 线性一致性读写与状态机应用顺序。

**必须处理**

- 同一个客户端请求到达多个 Leader 或被重复发送。
- Raft 已提交但服务端响应丢失，客户端再次发送相同请求。
- 服务端在提交后、向等待者通知前崩溃。
- 日志中出现相同客户端序列号时，状态机结果必须稳定。

**验收**

- 官方线性一致 KV 测试通过。
- 使用历史记录检查器验证并发 Put/Get 的线性化点。
- 给出“请求只执行一次”和“请求效果幂等一次”的精确定义。

### Lab 4：分片 KV 与配置变更

**核心能力**

- Shard Controller 的配置状态机。
- 多个 Raft Group 的分片所有权、迁移、快照和垃圾回收。
- 配置切换期间的读写线性一致性。

**迁移状态建议**

```text
Serving -> Pulling -> Serving
Serving -> Bequeathing -> GarbageCollected
```

实际状态名以课程版本为准，但必须显式表示：数据由谁负责、迁移是否完成、旧副本何时可以删除。

**故障场景**

- 配置服务在变更时分区。
- 源 Group 迁移数据后崩溃，目标 Group 重复拉取。
- 配置连续变化，旧迁移尚未结束又产生新配置。
- 客户端请求落到不拥有该 Shard 的 Group。

**验收**

- 官方 ShardKV 测试通过。
- 在 1000 次随机配置变化和节点故障下无数据丢失、回退或重复应用。
- 画出配置版本、Shard 版本和数据垃圾回收的依赖关系。

## 4. 课程之后的三个扩展项目

### 项目 A：生产化复制状态机（Go）

在 Lab 2/3 基础上实现一个可部署的 KV 服务：

- gRPC/HTTP API、客户端路由、Leader 重定向和请求超时。
- WAL 分段、校验和、压缩、Snapshot 上传和恢复演练。
- 动态成员变更、滚动升级、指标和 Trace。
- 支持线性一致读与明确标注的廉价读路径。
- 使用故障注入器随机杀进程、阻断网络、制造磁盘慢写。

**完成定义**：三节点和五节点集群在单节点崩溃、网络分区、滚动升级后保持已提交数据；恢复时间、吞吐和 P99 有可重复报告。

### 项目 B：Saga + Outbox 交易系统（Java）

选择订单、库存、支付、履约四个服务，至少实现：

- 每个服务本地事务和 Outbox 表。
- Relay 扫描、发布、重试、死信和幂等消费。
- Saga 编排器持久化步骤状态、补偿状态和业务关联 ID。
- 正向步骤超时、重复消息、乱序消息、补偿失败、人工重试。
- 对账任务发现本地状态与事件状态不一致。
- 明确中间状态对外可见的产品语义。

**必须演示的故障**

1. 本地事务提交成功但 Relay 进程立即崩溃。
2. 消息已被消费但 ACK 丢失，导致重复投递。
3. 支付成功后库存服务不可用。
4. 取消补偿本身失败，进入人工处理队列。
5. 用户重复点击导致同一业务命令重复到达。

**完成定义**：不会因为消息重复而重复扣库存或重复退款；每个订单最终进入可解释的完成、取消、人工处理或对账状态；所有状态转换可追踪。

### 项目 C：分布式存储或流处理系统

二选一，优先选择与职业方向不同的项目补足能力。

**存储方向**

- LSM、WAL、Compaction、Bloom Filter、MVCC、Range Sharding。
- 副本读写、Repair、再均衡、热点 Key 和故障恢复。

**流处理方向**

- 分区日志、Consumer Group、状态后端、Checkpoint、Watermark。
- 重放、乱序、背压、Schema 演进和端到端效果一次。

**完成定义**：故障恢复后的结果与无故障运行一致；可给出吞吐、恢复时间、P99、状态大小和资源成本报告。

## 5. 故障注入清单

### 网络

- 延迟、丢包、重复、乱序、半开连接、单向可达。
- 只丢请求、只丢响应、连接建立成功但响应迟到。
- 多数派/少数派分区，跨机房链路抖动。

### 进程与机器

- 任意时刻 SIGKILL、暂停进程、时钟跳变、磁盘只读、磁盘慢写。
- OOM、文件描述符耗尽、CPU 饱和、内存压力和 GC 长暂停。

### 数据与配置

- 重复命令、乱序事件、旧配置、Schema 不兼容、部分快照、损坏日志尾部。
- 热点 Key、突发流量、消费者积压、再均衡和滚动升级。

每个故障至少记录：注入时刻、影响范围、客户端可见结果、系统最终状态、恢复动作和是否需要人工介入。

## 6. 测试和验证工具

- Go：`go test -race`、`go test -run`、`go test -count`、pprof、fuzzing。
- 一致性：线性化历史检查器、Jepsen/Elle 思路、模型状态机对照测试。
- 规格：TLA+、PlusCal、Alloy；先写小模型验证不变量，再优化实现。
- 故障：toxiproxy、tc/netem、容器 kill/pause、磁盘故障模拟器。
- 可观测性：OpenTelemetry、Prometheus、Grafana、Jaeger、结构化事件日志。
- 性能：wrk、ghz、k6、fio、iperf3、Go benchmark。

## 7. 最终验收 Rubric

### A. 正确性（40 分）

- 官方课程测试通过：15 分。
- 安全性不变量和状态机说明：10 分。
- 随机故障、竞态、线性一致性/隔离级别测试：15 分。

### B. 故障恢复（20 分）

- 进程崩溃、网络分区、消息重复/乱序、磁盘恢复：10 分。
- 恢复时间、数据修复和人工介入路径可解释：10 分。

### C. 工程质量（20 分）

- API、配置、持久化格式、升级和兼容性：5 分。
- 指标、日志、Trace、告警和运行手册：5 分。
- 性能基线和瓶颈分析：5 分。
- 代码审查、测试可重复和文档完整：5 分。

### D. 理论与表达（20 分）

- 精读论文笔记和论文到实现的映射：10 分。
- 30 分钟架构答辩：10 分。

总分 80 分以上才算完成；任何安全性错误、已提交数据丢失或无法解释的恢复状态都会阻止通过，无论性能分数多高。

## 8. 最终答辩问题

1. 你的系统模型是什么？哪些故障不在保证范围内？
2. 一个客户端超时后重试，原请求可能处于哪些状态？
3. 如何证明同一日志 index 不会在两个副本应用不同命令？
4. 2PC 协调者崩溃时，参与者为什么可能阻塞？你怎样改善可用性？
5. Saga 补偿失败时，哪些状态已经对外可见？
6. 你的“Exactly-once”究竟覆盖哪一段链路？
7. 为什么这个系统选择强一致、因果一致或最终一致？
8. 热点分片、长尾延迟和重试风暴如何相互放大？
9. 恢复时先应用日志还是先安装快照？边界是什么？
10. 你最重要的一个设计假设如何被测试证伪过？
