# 电商卡券系统高并发技术设计

评审主 RD：待补充

## 一、背景与目标

### 1.1 背景

电商卡券系统需要支持 C 端用户查看自己的卡券列表，列表分为三类：

1. 未使用
2. 已使用
3. 已过期

在大促、直播、站内活动、私域投放等场景下，卡券系统还需要承受高并发领取、高并发列表查询、高并发下单锁券和支付核销。

### 1.2 对标说明

本文提到“对标京东、阿里”不是复刻其内部实现。京东、阿里内部卡券系统的表结构、缓存模型和 MQ 方案并未公开，不能假设其内部细节。本文对标的是头部电商可观察到的产品能力和业界通用大促架构能力：

1. C 端有清晰的可用、已用、过期列表。
2. 可用券不会因为缓存延迟而被实际核销。
3. 领取和核销链路具备幂等、防超发、防重复使用能力。
4. 订单链路以服务端强校验为准，前端列表只做展示。
5. 大流量读请求走缓存和读模型，核心状态变更走数据库条件更新。
6. 过期处理允许异步推进，但在线核销必须实时判断有效期。

### 1.3 本次目标

1. 设计卡券模板、用户卡券、状态流转、列表查询的可落地模型。
2. 支持未使用、已使用、已过期三类列表的高并发查询。
3. 支持高并发领券、下单锁券、支付核销、订单取消返还、自然过期。
4. 保证核心链路不超发、不重复核销、不核销过期券。
5. 支持后续横向扩展到多业务线、多券类型、多活动渠道。

### 1.4 非目标

1. 不在本设计里实现完整营销规则引擎。
2. 不设计复杂跨店铺、跨平台结算分摊。
3. 不假设前端倒计时具备最终判定能力。
4. 不把全量历史卡券常驻 Redis。

## 二、核心结论

### 2.1 方案结论

卡券系统采用“数据库强状态 + Redis 读模型 + MQ 事件驱动 + 过期时间轮”的方案。

1. MySQL 中的 `user_coupon` 是用户卡券状态的最终事实表。
2. Redis 只承接高频读、库存预扣、用户列表前几页缓存，不作为最终事实。
3. 卡券核销必须走数据库条件更新，不能只依赖 Redis 状态。
4. 未使用、已使用、已过期是 C 端展示状态，不完全等同于内部操作状态。
5. 自然过期用异步任务推进物理状态，在线读和在线核销必须实时判断 `valid_end_time`。
6. 用户卡券表按 `user_id` 分库分表，保证用户列表查询只落到一个分片。
7. 列表分页使用游标分页，不使用大 offset。

### 2.2 状态分层

内部操作状态建议设计为：

| 状态 | 名称 | 含义 | 是否可核销 |
| --- | --- | --- | --- |
| 1 | ISSUED | 已发放，未锁定，未使用 | 需要继续判断有效期 |
| 2 | LOCKED | 已被订单锁定，等待支付或取消 | 不可被其他订单核销 |
| 3 | USED | 已支付核销 | 否 |
| 4 | EXPIRED | 已过期 | 否 |
| 5 | INVALID | 人工作废或风控作废 | 否 |

C 端三类列表建议映射为：

| C 端列表 | 映射规则 | 说明 |
| --- | --- | --- |
| 未使用 | `status = ISSUED` 且 `valid_start_time <= now < valid_end_time` | 可用列表，最终核销仍走服务端校验 |
| 未使用，订单占用 | `status = LOCKED` 且订单未完结 | 如果产品只允许三类列表，可归到未使用但 `usable=false`，展示“订单占用中” |
| 已使用 | `status = USED` | 按 `used_time` 倒序 |
| 已过期 | `status = EXPIRED`，或 `status = ISSUED` 且 `valid_end_time <= now` | 后者是异步过期任务滞后的兜底展示 |

如果产品不希望展示订单占用券，可以在未使用列表过滤 `LOCKED`。本文默认 C 端未使用列表只展示 `ISSUED`，订单占用券由订单详情感知，避免用户在卡券页误操作。

### 2.3 核心不变量

1. 一张用户卡券只能被一个订单成功锁定。
2. 一张用户卡券只能从 `LOCKED` 成功流转到 `USED` 一次。
3. `valid_end_time <= now` 的卡券不能从 `ISSUED` 进入 `LOCKED`。
4. 已使用券不能因为自然过期任务被改成已过期。
5. 取消订单释放锁定券时，如果已经超过有效期，则进入 `EXPIRED`，不能回到 `ISSUED`。
6. 列表缓存可以短暂延迟，但下单锁券不能接受脏状态。

## 三、领域模型

### 3.1 卡券模板

卡券模板描述券的基本能力，例如满减券、折扣券、包邮券、兑换券。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `template_id` | 券模板 ID |
| `coupon_type` | 券类型，例如满减、折扣、包邮 |
| `issue_type` | 发放方式，例如用户领取、系统发放、活动中奖 |
| `total_stock` | 总库存 |
| `remain_stock` | 数据库剩余库存，最终对账使用 |
| `max_per_user` | 单用户最大领取数量 |
| `receive_start_time` | 领取开始时间 |
| `receive_end_time` | 领取结束时间 |
| `valid_type` | 有效期类型，固定时间或领取后 N 天 |
| `valid_start_time` | 固定有效期开始时间 |
| `valid_end_time` | 固定有效期结束时间 |
| `relative_valid_days` | 相对有效期天数 |
| `threshold_amount` | 使用门槛 |
| `discount_amount` | 优惠金额 |
| `rule_snapshot` | 规则快照 |
| `status` | 模板状态 |

### 3.2 用户卡券

用户卡券是用户真正拥有的一张券，是订单核销的最小单位。

核心字段：

| 字段 | 说明 |
| --- | --- |
| `coupon_id` | 用户卡券 ID，全局唯一 |
| `user_id` | 用户 ID，分库分表路由键 |
| `template_id` | 券模板 ID |
| `status` | 内部操作状态 |
| `valid_start_time` | 用户券实际有效开始时间 |
| `valid_end_time` | 用户券实际有效结束时间 |
| `receive_time` | 发放或领取时间 |
| `lock_time` | 下单锁券时间 |
| `used_time` | 支付核销时间 |
| `expire_time` | 过期落库时间，默认等于 `valid_end_time` |
| `order_id` | 当前锁定或已核销订单 |
| `request_no` | 领取或发放幂等号 |
| `rule_snapshot` | 发放时规则快照 |
| `version` | 乐观锁版本 |

### 3.3 操作流水

每次领取、锁定、核销、释放、过期、作废都写操作流水。

流水用于：

1. 幂等判断。
2. 客诉排查。
3. 财务和运营对账。
4. MQ 消费补偿。
5. 状态异常修复。

## 四、数据库设计

### 4.1 分库分表策略

用户卡券表按 `user_id` 分库分表：

```text
db_index = hash(user_id) % db_count
table_index = hash(user_id) % table_count
table_name = user_coupon_${table_index}
```

这样设计的原因：

1. 用户卡券列表天然按 `user_id` 查询，可以命中单个分片。
2. 下单时订单服务通常已知 `user_id`，可以直接路由到用户券分片。
3. 用户维度的数据冷热分布更适合列表缓存和历史归档。

后台按 `coupon_id` 查询时需要解决路由问题。建议 `coupon_id` 使用雪花 ID 并在低位编码 `user_hash`，或者维护 `coupon_route` 小表。优先推荐在 `coupon_id` 编码路由信息，减少后台查询二次索引依赖。

## 五、Redis 设计

### 5.1 Redis 使用边界

Redis 负责：

1. 热门券模板库存预扣。
2. 用户领取次数快速判断。
3. 用户卡券列表前几页读模型。
4. 卡券详情短期缓存。
5. 过期时间轮或过期桶。

Redis 不负责：

1. 最终核销状态判定。
2. 财务对账。
3. 全量历史卡券长期存储。
4. 跳过数据库直接完成用券。

### 5.2 Key 设计

| Key | 类型 | 说明 | TTL |
| --- | --- | --- | --- |
| `coupon:tpl:{templateId}` | String/Hash | 券模板缓存 | 5 到 30 分钟，变更主动删除 |
| `coupon:stock:{templateId}` | String | 热门模板 Redis 库存 | 活动结束后 1 天 |
| `coupon:recv:{templateId}:{userId}` | String | 用户领取数量 | 活动结束后 1 天 |
| `coupon:{userId}:list:unused` | ZSet | 用户未使用列表 | 最近访问后 7 到 30 天 |
| `coupon:{userId}:list:used` | ZSet | 用户已使用列表前 N 条 | 最近访问后 7 到 30 天 |
| `coupon:{userId}:list:expired` | ZSet | 用户已过期列表前 N 条 | 最近访问后 7 到 30 天 |
| `coupon:{userId}:list:unused:expire` | ZSet | 用户未使用券过期索引 | 跟随未使用列表 |
| `coupon:detail:{couponId}` | String/Hash | 用户券详情 | 按有效期加 7 天 |
| `coupon:{userId}:count` | Hash | 三类列表计数 | 最近访问后 7 到 30 天 |
| `coupon:expire:bucket:{yyyyMMddHHmm}` | ZSet/List | 分钟级过期桶 | 消费完成后 1 天 |

Redis Cluster 下同一个用户的列表 key 建议使用 hash tag，例如 `coupon:{u_123}:list:unused`，保证用户维度多 key 操作可以落在同一个 slot。

### 5.3 列表排序

未使用列表建议默认排序：

1. 即将过期优先。
2. 优惠力度高优先。
3. 领取时间晚优先。
4. `coupon_id` 兜底稳定排序。

示例 score：

```text
unused_score = valid_end_epoch_seconds * 1000000 - benefit_weight
```

Redis double 对秒级时间乘以一百万仍可保持整数精度。若排序规则更复杂，可以将 Redis 只作为 ID 索引，详情排序在应用侧对当前页候选集合完成，但不要一次拉取用户全量卡券。

已使用列表排序：

```text
used_score = used_time_epoch_millis
```

查询时倒序返回。

已过期列表排序：

```text
expired_score = expire_time_epoch_millis
```

查询时倒序返回。

### 5.4 不全量缓存历史卡券

不能把全量用户历史卡券永久放 Redis，原因是内存不可控。建议：

1. 未使用列表缓存用户当前全部可用券，因为单用户可用券数量通常可控。
2. 已使用、已过期列表只缓存前 N 条，例如前 100 条或前 200 条。
3. 深分页走 MySQL 游标分页。
4. 已过期和已使用历史超过 180 天进入归档表或离线存储。
5. 用户列表 key 设置滑动 TTL，长期不访问自动淘汰。

## 六、卡券列表查询设计

### 6.1 API 设计

```http
GET /api/coupon/user/list?state=UNUSED&cursor=xxx&pageSize=20
```

请求参数：

| 参数 | 说明 |
| --- | --- |
| `state` | `UNUSED`、`USED`、`EXPIRED` |
| `cursor` | 游标，第一页为空 |
| `pageSize` | 每页数量，建议最大 50 |

返回字段：

| 字段 | 说明 |
| --- | --- |
| `items` | 卡券列表 |
| `nextCursor` | 下一页游标 |
| `hasMore` | 是否还有更多 |
| `serverTime` | 服务端时间，前端倒计时使用 |
| `counts` | 三类列表计数，可允许秒级最终一致 |

卡券 item 字段：

| 字段 | 说明 |
| --- | --- |
| `couponId` | 用户券 ID |
| `templateId` | 模板 ID |
| `displayState` | C 端展示状态 |
| `usable` | 当前是否可用 |
| `unusableReason` | 不可用原因 |
| `validStartTime` | 有效开始时间 |
| `validEndTime` | 有效结束时间 |
| `thresholdAmount` | 门槛 |
| `discountAmount` | 优惠 |
| `ruleDesc` | 规则文案 |

### 6.2 查询主流程

```text
1. 获取 userId。
2. 根据 state 读取对应 Redis ZSet。
3. 如果 Redis 命中，批量 MGET 卡券详情。
4. 对返回结果做服务端二次过滤，过滤掉已过期、状态不匹配、已删除数据。
5. 如果过滤后数量不足，继续从 Redis 下一段或回源 DB 补齐。
6. 如果 Redis 未命中，按 userId 路由到分片 DB，使用游标分页查询。
7. DB 返回后异步重建该用户对应 state 的前几页缓存。
8. 返回 `serverTime`，前端倒计时必须基于该时间。
```

### 6.3 未使用列表查询

未使用列表必须保证不展示已过期券。即使异步过期任务滞后，在线查询也要用 `valid_end_time > now` 兜底。

Redis 命中时：

```text
1. 先对 `coupon:{userId}:list:unused:expire` 执行到期券懒修复。
2. 找出 `valid_end_time <= now` 的 couponId。
3. 从 unused ZSet 删除这些 couponId。
4. 加入 expired ZSet。
5. 异步发送过期修复事件，推进 DB 状态。
6. 再读取 unused ZSet 当前页。
```

DB 回源 SQL 示例：

```sql
SELECT *
FROM user_coupon_00
WHERE user_id = ?
  AND status = 1
  AND valid_start_time <= ?
  AND valid_end_time > ?
  AND deleted = 0
  AND (valid_end_time, coupon_id) > (?, ?)
ORDER BY valid_end_time ASC, coupon_id ASC
LIMIT ?;
```

第一页游标为空时不带最后一行条件。MySQL 版本不支持行比较时，改成：

```sql
AND (
  valid_end_time > ?
  OR (valid_end_time = ? AND coupon_id > ?)
)
```

### 6.4 已使用列表查询

DB 回源 SQL 示例：

```sql
SELECT *
FROM user_coupon_00
WHERE user_id = ?
  AND status = 3
  AND deleted = 0
  AND (
    used_time < ?
    OR (used_time = ? AND coupon_id < ?)
  )
ORDER BY used_time DESC, coupon_id DESC
LIMIT ?;
```

已使用列表只读历史数据，允许缓存前 N 条。核销成功后通过 MQ 将券从未使用列表删除并加入已使用列表。

### 6.5 已过期列表查询

已过期列表不要在主查询里长期使用 `status = EXPIRED OR valid_end_time <= now`，这个 OR 会破坏索引稳定性。

推荐流程：

```text
1. 查询前先做用户维度过期懒修复，单次最多处理 200 条。
2. 懒修复将 `status=ISSUED AND valid_end_time<=now` 的券更新为 `EXPIRED`。
3. 懒修复写状态流水和 outbox。
4. 主查询只查 `status=EXPIRED`。
5. 如果用户存在大量历史券，超过本次修复上限的部分交给异步任务继续推进。
```

懒修复 SQL 示例：

```sql
UPDATE user_coupon_00
SET status = 4,
    expire_time = valid_end_time,
    updated_at = NOW(3)
WHERE user_id = ?
  AND status = 1
  AND valid_end_time <= ?
  AND deleted = 0
ORDER BY valid_end_time ASC
LIMIT 200;
```

已过期主查询 SQL 示例：

```sql
SELECT *
FROM user_coupon_00
WHERE user_id = ?
  AND status = 4
  AND deleted = 0
  AND (
    expire_time < ?
    OR (expire_time = ? AND coupon_id < ?)
  )
ORDER BY expire_time DESC, coupon_id DESC
LIMIT ?;
```

### 6.6 计数设计

三类列表 tab 计数不要每次实时 `COUNT(*)`。建议：

1. Redis Hash 保存 `unused_count`、`used_count`、`expired_count`。
2. 领取、核销、过期、作废事件驱动计数变更。
3. 用户访问列表时做小范围懒修复，修正当前用户过期导致的计数偏差。
4. 缓存丢失时，第一页可以不返回精确计数，或者异步计算后下次返回。
5. 运营后台需要精确统计时走离线数仓或专用汇总表。

计数一致性要求：

| 场景 | 一致性要求 |
| --- | --- |
| C 端 tab 展示 | 允许秒级最终一致 |
| 下单可用券判断 | 必须强一致校验 |
| 财务和结算 | 必须以 DB 和流水为准 |
| 运营报表 | 使用离线汇总 |

## 七、高并发领取设计

### 7.1 领取流程

```text
1. 校验模板状态、领取时间、活动渠道。
2. 使用 requestNo 做请求幂等。
3. Redis Lua 原子判断用户限领和库存。
4. Redis 预扣成功后写 user_coupon。
5. 同事务写 coupon_status_log 和 coupon_outbox。
6. outbox 消息投递后更新用户列表缓存和计数。
7. 如果 DB 写入失败，发送库存补偿或同步回滚 Redis 预扣。
```

### 7.2 Redis Lua 需要保证的操作

Lua 内部完成：

1. 判断活动是否仍可领取。
2. 判断用户领取数量是否小于 `max_per_user`。
3. 判断库存是否大于 0。
4. 库存扣减。
5. 用户领取计数增加。
6. 记录短期幂等标记。

注意：

1. Lua 成功不代表用户券已经最终发放成功。
2. 如果业务要求领券接口必须同步返回券 ID，则 DB 插入必须在接口内完成。
3. 如果是极端大促，可以返回“发放中”，由异步消费者创建用户券，但前端需要接受列表短暂延迟。

### 7.3 数据库兜底防超发

Redis 预扣可以抗高并发，但不能替代数据库最终对账。模板库存建议保留 DB 条件更新能力：

```sql
UPDATE coupon_template
SET remain_stock = remain_stock - 1
WHERE id = ?
  AND remain_stock > 0
  AND status = 1;
```

高峰期不建议每次领取都同步更新模板主表库存，否则热门券会产生单行热点。可选方案：

1. 小活动使用 DB 条件更新，简单可靠。
2. 大活动使用 Redis 预扣加库存分片表。
3. 超大活动按库存段预热到多个 Redis key，消费者异步汇总 DB 库存。

库存分片表示例：

```text
coupon_stock_segment(template_id, segment_no, total_stock, remain_stock)
```

领取时按用户 hash 或随机选择库存段，避免单行热点。

### 7.4 幂等设计

幂等维度：

| 场景 | 幂等键 |
| --- | --- |
| 用户主动领取 | `userId + templateId + requestNo` |
| 活动批量发券 | `activityId + userId + templateId` |
| 订单锁券 | `orderId + couponId` |
| 支付核销 | `payId + orderId + couponId` |
| 订单取消释放 | `orderId + couponId + cancelEventId` |
| 自然过期 | `couponId + validEndTime` |

幂等结果必须返回上次成功结果，不能简单报错。

## 八、下单锁券与核销设计

### 8.1 下单预览

下单预览用于展示可用券和不可用原因，不改变券状态。

流程：

```text
1. 批量查询用户未使用券。
2. 批量加载模板和适用范围缓存。
3. 在内存中匹配商品、SKU、店铺、类目、金额门槛。
4. 返回最优券、可用券列表、不可用原因。
```

注意：

1. 不能在循环中逐张券调用商品 RPC、库存 RPC 或规则 RPC。
2. 商品、SKU、店铺信息必须批量查询。
3. 规则快照优先使用用户券快照，避免模板修改影响已发券。

### 8.2 下单锁券

订单提交时必须执行数据库条件更新：

```sql
UPDATE user_coupon_00
SET status = 2,
    order_id = ?,
    lock_time = NOW(3),
    version = version + 1,
    updated_at = NOW(3)
WHERE coupon_id = ?
  AND user_id = ?
  AND status = 1
  AND valid_start_time <= NOW(3)
  AND valid_end_time > NOW(3)
  AND deleted = 0;
```

更新成功才代表锁券成功。更新失败需要返回明确原因：

1. 不存在。
2. 已使用。
3. 已过期。
4. 已被其他订单锁定。
5. 不满足规则。

### 8.3 支付核销

默认规则：只要订单在券有效期内成功锁券，支付在订单支付有效期内完成，就可以从 `LOCKED` 流转到 `USED`。如果业务要求“支付成功时券仍必须有效”，需要在支付核销 SQL 中增加 `valid_end_time > NOW(3)`。

支付核销 SQL：

```sql
UPDATE user_coupon_00
SET status = 3,
    used_time = NOW(3),
    version = version + 1,
    updated_at = NOW(3)
WHERE coupon_id = ?
  AND user_id = ?
  AND order_id = ?
  AND status = 2
  AND deleted = 0;
```

同事务写状态流水和 outbox。outbox 消费后：

1. 从未使用列表删除。
2. 从过期索引删除。
3. 加入已使用列表。
4. 更新用户计数。
5. 删除或刷新详情缓存。

### 8.4 订单取消和超时释放

释放锁券时根据当前时间决定目标状态：

```text
if now < valid_end_time:
    LOCKED -> ISSUED
else:
    LOCKED -> EXPIRED
```

SQL 示例：

```sql
UPDATE user_coupon_00
SET status = CASE WHEN valid_end_time > NOW(3) THEN 1 ELSE 4 END,
    expire_time = CASE WHEN valid_end_time > NOW(3) THEN expire_time ELSE valid_end_time END,
    order_id = NULL,
    version = version + 1,
    updated_at = NOW(3)
WHERE coupon_id = ?
  AND user_id = ?
  AND order_id = ?
  AND status = 2
  AND deleted = 0;
```

注意：释放锁券必须由订单状态机驱动，不能只依赖卡券系统自行判断。

## 九、过期处理设计

### 9.1 过期处理原则

1. `valid_end_time` 是是否过期的最终判断依据。
2. `status=EXPIRED` 是异步落库后的物理状态。
3. 在线锁券必须实时判断 `valid_end_time > now`。
4. 在线未使用列表必须过滤 `valid_end_time <= now`。
5. 过期任务只处理 `ISSUED`，不能处理 `USED`。
6. `LOCKED` 券是否可自然过期由订单释放流程决定，避免支付和过期任务互相覆盖。

### 9.2 时间轮方案

不建议为每张券发送单独延迟消息。千万级券会给延迟消息系统带来巨大压力。

推荐分钟级时间轮：

```text
bucket = format(valid_end_time, yyyyMMddHHmm)
coupon:expire:bucket:{bucket} -> couponId list
```

发券成功后将 `couponId` 写入对应过期桶。过期 worker 每分钟扫描当前和历史未完成 bucket：

```text
1. 读取到期 bucket。
2. 按 user_id 路由分片。
3. 批量更新 `status=ISSUED AND valid_end_time<=now` 的券为 EXPIRED。
4. 写状态流水和 outbox。
5. 消费 outbox 更新 Redis 列表。
6. bucket 处理完成后打标，失败则重试。
```

### 9.3 分片扫描兜底

如果过期桶丢失或 MQ 积压，需要分片扫描兜底：

```sql
SELECT coupon_id, user_id
FROM user_coupon_00
WHERE status = 1
  AND valid_end_time <= NOW(3)
ORDER BY valid_end_time ASC
LIMIT 1000;
```

然后批量更新：

```sql
UPDATE user_coupon_00
SET status = 4,
    expire_time = valid_end_time,
    updated_at = NOW(3)
WHERE status = 1
  AND valid_end_time <= NOW(3)
  AND coupon_id IN (...);
```

兜底扫描要限速，避免和在线下单、列表查询抢资源。

## 十、缓存一致性设计

### 10.1 事件驱动

所有状态变化都产生事件：

| 事件 | 触发时机 | 缓存动作 |
| --- | --- | --- |
| `CouponIssued` | 发券成功 | 加入未使用列表，更新计数 |
| `CouponLocked` | 下单锁券成功 | 从可用候选中移除，刷新详情 |
| `CouponUsed` | 支付核销成功 | 加入已使用列表，更新计数 |
| `CouponReleased` | 订单取消释放 | 回到未使用或进入已过期 |
| `CouponExpired` | 自然过期 | 加入已过期列表，更新计数 |
| `CouponInvalidated` | 作废 | 从 C 端列表移除或进入不可用列表 |

事件必须可重放，消费必须幂等。Redis 更新失败时不回滚 DB，依赖重试和读时修复。

### 10.2 本地消息表

DB 状态变更和 outbox 写入放在同一个事务：

```text
BEGIN;
UPDATE user_coupon ...
INSERT coupon_status_log ...
INSERT coupon_outbox ...
COMMIT;
```

后台投递器扫描 `coupon_outbox`，发送 MQ 成功后标记已发送。消费者更新 Redis。

优点：

1. 避免 DB 成功但 MQ 丢消息。
2. 支持失败重试。
3. 支持人工补偿。

### 10.3 读时修复

列表查询时发现 Redis 数据和 DB 或有效期不一致，执行轻量修复：

1. Redis 中未使用券已过期，先从当前返回结果中过滤。
2. 异步发送 `CouponExpireRepair`。
3. 详情缓存状态错误，删除详情缓存。
4. 单用户异常数据较多时，触发用户级缓存重建。

读时修复只做小批量，避免单个异常用户拖慢接口。

## 十一、规则与适用范围

### 11.1 规则快照

用户券必须保存发放时的规则快照。原因：

1. 模板规则修改不应影响已发券，除非明确做运营变更。
2. 订单核销和客诉需要还原当时规则。
3. 缓存重建不依赖模板历史版本。

### 11.2 适用范围

适用范围可以独立建表：

```text
coupon_template_scope(template_id, scope_type, target_id)
```

`scope_type` 示例：

| 类型 | 说明 |
| --- | --- |
| 1 | 全场 |
| 2 | 店铺 |
| 3 | 类目 |
| 4 | 商品 |
| 5 | SKU |
| 6 | 品牌 |

订单预览时必须批量加载用户券、模板、范围、商品信息，一次性在内存匹配，避免循环 RPC。

### 11.3 最优券计算

最优券计算建议独立服务方法，不放在列表接口里。列表接口只负责展示用户已有券，订单预览负责计算当前订单可用性和最优优惠。

## 十三、异常场景处理

### 13.1 Redis 扣库存成功但 DB 写失败

处理方式：

1. 同步回滚 Redis 库存和用户领取计数。
2. 如果同步回滚失败，写补偿任务。
3. 对外返回失败或发放中，不能返回已成功领取。

### 13.2 DB 成功但 MQ 失败

处理方式：

1. 依赖 outbox 后台重试。
2. 列表短暂不可见可以接受。
3. 用户主动刷新时 DB 回源可看到真实数据。

### 13.3 Redis 列表里存在已使用券

处理方式：

1. 详情校验发现 `status != ISSUED`，当前响应过滤。
2. 删除该 couponId 的详情缓存。
3. 异步修复用户列表 ZSet。

### 13.4 过期任务积压

处理方式：

1. 未使用列表在线过滤 `valid_end_time <= now`。
2. 锁券 SQL 强制 `valid_end_time > now`。
3. 已过期列表查询前做用户维度懒修复。
4. 后台分片扫描限速补偿。

### 13.5 重复支付回调

处理方式：

1. 核销 SQL 条件必须包含 `status = LOCKED`。
2. 状态流水用 `request_no` 幂等。
3. 第二次回调返回第一次成功结果。

### 13.6 订单取消和支付并发

处理方式：

1. 订单服务保证订单状态机单向流转。
2. 卡券系统 SQL 条件更新兜底。
3. `LOCKED -> USED` 和 `LOCKED -> ISSUED/EXPIRED` 只有一个能成功。
4. 失败方查询最新状态并返回幂等结果。

## 十四、性能与容量设计

### 14.1 容量假设

设计按以下量级预估：

| 指标 | 目标 |
| --- | --- |
| 用户券年增量 | 10 亿级 |
| 单用户未使用券 | 通常小于 100 |
| 领券峰值 QPS | 10 万级 |
| 列表查询峰值 QPS | 5 万级 |
| 锁券和核销峰值 QPS | 1 万到 5 万级 |
| Redis 列表命中率 | 大于 90% |
| 未使用列表 P99 | 小于 100ms |
| 锁券 P99 | 小于 200ms |

### 14.2 关键优化

1. 用户券按 `user_id` 分库分表，列表查询单分片完成。
2. 用户列表只缓存热数据和前几页历史数据。
3. 分页使用 cursor，不使用大 offset。
4. 领取库存使用 Redis Lua 预扣，热门模板使用库存分片。
5. 核心状态变更使用 DB 条件更新，不加分布式锁。
6. MQ 消费批量更新 Redis，避免单条消息单次网络往返。
7. 订单预览批量加载商品和券规则，不在循环中调用外部依赖。
8. 过期任务按分钟桶批处理，不使用海量单券延迟消息。

### 14.3 限流与降级

领券接口：

1. 按模板限流。
2. 按用户限流。
3. 按 IP 和设备限流。
4. 热门券可开启排队或异步发放。

列表接口：

1. Redis 故障时回源 DB 只允许第一页。
2. 计数接口可降级为不返回或返回缓存旧值。
3. 深分页限流。
4. 单用户异常大列表限制最大扫描数量。

订单核销：

1. 不能降级为跳过卡券校验。
2. Redis 故障不影响 DB 锁券和核销。
3. MQ 故障只影响列表刷新，不影响订单状态。

## 十五、安全与风控

### 15.1 防刷

1. 领券接口要求登录态。
2. 热门模板按用户、设备、IP、渠道限流。
3. requestNo 不能由服务端无脑信任，需要结合用户和模板做幂等。
4. 高价值券可增加风控校验。

### 15.2 防篡改

1. 前端不能传优惠金额，优惠金额以服务端规则和用户券快照为准。
2. 前端不能传有效期，服务端按 DB 判断。
3. 订单金额、商品范围必须由服务端重新计算。

### 15.3 审计

## 十九、关键取舍

### 19.1 为什么不只用 `status` 做三态

只用 `status` 会遇到自然过期滞后问题。比如券 10:00 过期，过期任务 10:05 才处理，如果只看 `status=ISSUED`，10:01 仍可能展示为未使用。正确做法是：

1. 在线可用判断必须同时看 `status` 和 `valid_end_time`。
2. 后台任务异步把物理状态推进到 `EXPIRED`。
3. 列表读模型允许修复，但核销不允许放过。

### 19.2 为什么不每次列表都查 DB

大促期间卡券页、下单页、领券后刷新都会带来高 QPS。每次都查 DB 会导致用户券分片压力过大。Redis 读模型可以吸收高频读，DB 只承接缓存 miss、深分页和最终状态变更。

### 19.3 为什么不把所有历史券都缓存

历史已用和过期券规模很大，常驻 Redis 成本不可控。只缓存热用户和前几页历史数据，深分页回源 DB，是成本和性能更均衡的方案。

### 19.4 为什么不用分布式锁做核销

核销最终要落 DB，数据库条件更新天然具备并发互斥能力。额外分布式锁会增加链路复杂度和故障点，且锁异常释放会带来新问题。推荐用 `UPDATE ... WHERE status = ?` 做状态机 CAS。

## 二十、待业务确认点

1. 订单锁券后，如果券在支付前过期，支付成功时是否允许核销。本文默认允许，因为锁券发生在有效期内。
2. `LOCKED` 状态是否需要在 C 端卡券列表展示为“订单占用中”。本文默认不展示在未使用列表。
3. 已使用和已过期列表保留多久。建议 C 端保留 180 天，后台和数仓按合规要求保留更久。
4. 三类列表 tab 计数是否要求强一致。本文建议 C 端允许秒级最终一致。
5. 是否存在跨店铺分摊和平台补贴结算。如果存在，需要补充结算明细表。
